**When to use:** When starting a brand new Playwright automation project from scratch.

```bash
# Create project folder
```

| Prompt | Recommended Choice |

| Language | **TypeScript** |

```
my-automation-suite/
├── tests/

├── helpers/                     # Create this manually — shared utility functions
├── config/
│   └── .env.example             # Template showing required variables — commit this
├── playwright.config.ts         # Playwright configuration

├── package.json                 # Project dependencies and scripts
├── package-lock.json            # Exact dependency versions — always commit this
├── .github/
```

### 4️⃣ Playwright Configuration (`playwright.config.ts`)

A solid starting configuration for a TypeScript automation project:

```typescript
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';
import dotenv from 'dotenv';

dotenv.config();

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,      // Fail build if test.only is left in code on CI
  retries: process.env.CI ? 2 : 0,   // Retry failed tests 2x on CI; no retries locally
  workers: process.env.CI ? 1 : undefined,
  reporter: [
    ['html'],    // HTML report — view with: npx playwright show-report
    ['list'],    // Console output during test run
  ],
  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
    trace: 'on-first-retry',          // Capture trace on first retry for debugging
    screenshot: 'only-on-failure',
    video: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
  ],
});
```

## Part 1 — Git & GitHub Basics

### 🧠 What is Git?

Git is a **version control system** installed locally on your machine. As a QA automation engineer, Git:

- Tracks every change to your `.spec.ts` files, page objects, and config
- Saves a full project history — if you accidentally delete 50 test cases, Git can restore them
- Lets you experiment safely on a separate branch (try a new locator strategy, refactor page objects) without breaking the stable suite on `main`
- Lets your whole QA team write different tests simultaneously without overwriting each other

Think of Git as a permanent logbook of every change ever made to your test suite, with the ability to go back to any point in history.

### 🧠 What is GitHub?

GitHub is the **cloud platform** where your test repository lives online. For QA teams it provides:

- A central place to store and share all test scripts
- Pull Requests — teammates review new tests before they merge into the main suite
- **GitHub Actions** — automatically runs your Playwright tests on every PR; blocks merge if tests fail
- Visibility — developers and managers see test results directly on GitHub without needing to install anything

---

### ⚙️ First-Time Git Setup

**When to use:** Once per computer, right after installing Git.

```bash
git config --global user.name "Your Name"
git config --global user.email "your@email.com"

# Verify your settings
git config --list
```

Git uses this to label every commit with your name. Your team sees it next to every test you write or change.

## Part 2 — Authentication

GitHub no longer accepts plain passwords when pushing code. Use one of the following methods.

### 🔑 Method 1 — Personal Access Token (PAT)

**When to use:** In CI runners (Jenkins, self-hosted GitHub Actions runners) or any environment where interactive browser login is not possible.

1. GitHub → **Settings** → **Developer Settings** → **Personal Access Tokens → Tokens (classic)**
2. Click **Generate new token**
3. Give it a name (e.g., `playwright-ci-token`), set expiry, check the **`repo`** scope
4. Copy the token immediately — it is shown only once

When Git asks for a password during a push, paste the token.

> **In CI:** Store it as a GitHub Secret (repo Settings → Secrets and variables → Actions) and reference it as `${{ secrets.GITHUB_TOKEN }}`. Never hardcode it in workflow files.

---

### 🔑 Method 2 — GitHub CLI (Recommended for Local Work)

**When to use:** For day-to-day local work. Set up once; never type credentials again.

```bash
gh auth login
```

After browser login, all `git push` and `git pull` operations are authenticated automatically.

## Part 3 — Local → Private Repository Flow

Use this when you have **already started writing tests locally** and want to push them to a new GitHub repository.

### Step 1 — Initialize Git

**When to use:** Once per project, at the very beginning.

```bash
cd my-automation-suite
git init
```

Creates a hidden `.git/` folder — this is where Git stores your entire project history.

### Step 2 — Verify `.gitignore` Exists

Make sure your `.gitignore` is in place before staging anything (see Part 0). Never run `git add .` without it.

### Step 3 — Stage and Commit

```bash
git add .
git commit -m "Initial Playwright TypeScript test suite setup"
```

### Step 4 — Create Private Repo on GitHub and Push

**Option A — GitHub CLI (one command, recommended):**

```bash
gh repo create my-automation-suite --private --source=. --remote=origin --push
```

Creates the repo on GitHub, links it as `origin`, and pushes your code — all in one step.

**Option B — Manual:**

```bash
git remote add origin https://github.com/username/my-automation-suite.git
git branch -M main
git push -u origin main
```

> **What `-u` does:** Sets `origin main` as the default upstream so all future pushes only need `git push` — no additional arguments required.

Use this when a test repository **already exists on GitHub** and you need to work on it locally.

### Step 1 — Clone

**When to use:** The first time you download a project to a new machine.

```bash
# GitHub CLI (recommended)

# Standard Git
```


If tests fail before you've changed anything, raise it with your QA lead. Don't start writing new tests on top of an already-broken suite.

### Step 5 — Make Changes, Commit, Push

```bash
git add .
git commit -m "Add login smoke tests for staging environment"
git push
```

## Part 5 — Branching

### What is a Branch?

A branch is an **independent line of work**. You create a branch so that:

- Your in-progress tests don't break the stable suite on `main` for the whole team
- Multiple QA engineers can write tests simultaneously without conflicts
- Every change goes through a Pull Request review before it reaches `main`

```
main ──────────●────────────────────────●──────►  (always stable, CI always green)
                \                      /
                 ●────●────●──────────   test/checkout-flow (your branch)
```

### Branch Naming for QA Projects

| Branch Name | When to Use |
|-------------|-------------|
| `test/login-flow` | New test suite for a specific feature |
| `test/api-cart-endpoints` | Tests for specific API endpoints |
| `fix/checkout-flaky` | Fixing a flaky or broken existing test |
| `refactor/page-objects` | Restructuring Page Object Model classes |
| `chore/update-playwright` | Upgrading Playwright or other dependencies |

### Create and Switch to a Branch

**When to use:** Every time you start a new task. Never commit test work directly to `main`.

```bash
git checkout -b test/login-flow
```

### Check Your Current Branch

```bash
git branch
# The branch marked with * is your current location
```

### Push Your Branch to GitHub

**When to use:** To back up your work remotely, or when you're ready to open a Pull Request.

```bash
git push -u origin test/login-flow
```

### Delete a Branch After Merging

**When to use:** After your Pull Request is merged. Keeps the branch list clean — essential when the whole team is creating branches regularly.

```bash
git branch -d test/login-flow              # Delete from your local machine
git push origin --delete test/login-flow   # Delete from GitHub
```

## Part 6 — Confusing Commands Clearly Explained

This section covers the command pairs that trip up most people. Understanding the differences here prevents serious mistakes.

---

### 🔀 `git fetch` vs `git pull`

Both get changes from GitHub. The difference is what happens next.

#### `git fetch`

```bash
git fetch
# or more explicitly:
git fetch origin
```

**What it does:** Downloads the latest commits and branch information from GitHub into your local Git database — but does **not touch your working files at all**. Your code stays exactly as it is.

**Think of it as:** Asking "what has the team pushed?" without applying any of it yet.

**When to use:**
- You want to see what teammates pushed before deciding whether to merge or rebase
- You're about to run `git rebase origin/main` and want the absolute latest version of `main`
- You want to check if a remote branch exists without changing your files

```bash
# The standard pattern for updating a feature branch cleanly
git fetch origin
git rebase origin/main
```

---

#### `git pull`

```bash
git pull
```

**What it does:** `git fetch` + `git merge` combined into one step. Downloads changes from GitHub **and immediately merges them** into your current branch.

**Think of it as:** Applying the team's latest changes to your files right now.

**When to use:**
- You're on `main` at the start of the day and want it fully up to date
- You're on a shared branch and want the team's latest commits applied immediately
- You're confident there are no conflicts

```bash
# Most common use — start of day
git checkout main
git pull
```

#### Decision Guide: fetch vs pull

| Situation | Command |
|-----------|---------|
| Start of day, updating `main` | `git pull` |
| About to rebase your feature branch | `git fetch` then `git rebase origin/main` |
| Check what the team pushed without changing your files | `git fetch` |
| Quick sync on `main` with no conflicts expected | `git pull` |

---

### 🔀 `git merge` vs `git rebase`

Both integrate changes from one branch into another. They produce the same end result but with different history shapes — and different rules for when it's safe to use them.

#### `git merge`

```bash
git checkout main
git merge test/login-flow
```

**What it does:** Creates a new "merge commit" that joins the two branch histories. Both branches' complete history is preserved exactly as it happened.

**History shape:**

```
main    ──●──────────────────────────●── (new merge commit)
           \                        /
            ●────●────●────────────     test/login-flow
```

**When to use:**
- Merging an approved Pull Request into `main` — this is the standard way PRs are merged
- Integrating changes on a **shared** branch that multiple people are working on (rebasing a shared branch causes problems for others)
- When you want to preserve the full picture of what happened on each branch

```bash
# After PR is approved — merge the feature branch into main
git checkout main
git merge test/login-flow
git push
```

---

#### `git rebase`

```bash
git checkout test/login-flow
git rebase main
```

**What it does:** Takes your commits and **replays them one by one on top of** the latest `main`. No merge commit is created. Your branch history is rewritten to look as if you started your work from the very latest commit on `main`.

**History shape:**

```
Before rebase:
main    ──●──●──●                  (main has moved forward)
           \
            ●──●                   (your branch, behind)

After rebase:
main    ──●──●──●
                 \
                  ●──●             (your commits replayed on top — clean, linear)
```

**When to use:**
- Updating **your own private feature branch** with the latest `main` before opening a PR — produces a clean, linear history
- Before opening a PR to ensure no conflicts with current `main`
- **Only on branches that no one else has pulled locally**

```bash
# Keep your test branch current with main (do this daily)
git checkout main
git pull
git checkout test/login-flow
git rebase main
```

#### ⚠️ The Golden Rule of Rebase

**Never rebase a branch other people have already pulled.** Rebasing rewrites commit history. If a teammate has pulled your branch and you then force-push a rebased version, their local copy becomes incompatible with GitHub. Only rebase your **own private feature branches**.

#### Decision Guide: merge vs rebase

| Situation | Command |
|-----------|---------|
| Updating your own private feature branch with latest main | `git rebase main` |
| Merging an approved PR into main | `git merge` |
| Two engineers working on the same shared branch | `git merge` only — never rebase |
| Want a clean, linear history on a PR | `git rebase main` before opening the PR |
| Want to preserve full branch context in history | `git merge` |

---

### 🔀 `git reset` vs `git revert`

Both undo changes. The critical difference is whether the commit has been **pushed to GitHub** already.

#### `git reset`

```bash
git reset --soft HEAD~1    # Undo commit, keep changes staged
git reset --hard HEAD~1    # Undo commit and delete all changes permanently
```

**What it does:** Moves the branch pointer backward as if the commit(s) never happened. It **rewrites history**.

**When to use:** Only for commits that **have not been pushed yet**. Perfect for fixing local mistakes before anyone else sees them.

**When NOT to use:** After pushing. If teammates have pulled your commit, resetting and force-pushing will corrupt their local copy.

```bash
# Safe — undo a local commit before pushing
git reset --soft HEAD~1   # Keeps your test changes staged (ready to re-commit)
git reset --hard HEAD~1   # Permanently discards all changes from that commit
```

---

#### `git revert`

```bash
git revert <commit-hash>
```

**What it does:** Creates a **new commit** that reverses the effect of a previous one. The original commit stays in history — a new corrective commit is added on top.

**When to use:** When the bad commit has **already been pushed** to GitHub. This is the safe approach because it does not rewrite history — it only adds forward.

```bash
# Find the bad commit
git log --oneline
# e.g.: a3f9c21  Add checkout tests (broken config accidentally committed)

# Reverse it safely
git revert a3f9c21
git push
```

#### Decision Guide: reset vs revert

| Situation | Command |
|-----------|---------|
| Commit is local only, not pushed | `git reset` |
| Commit is already pushed to GitHub | `git revert` |
| Accidentally committed `.env` (not pushed) | `git reset --soft HEAD~1`, remove the file, re-commit |
| Broken test reached `main` | `git revert <hash>` then `git push` |
| Want a safe, auditable undo with full history | `git revert` |

---

### 🔀 `git restore --staged` vs `git reset HEAD` (Unstaging)

Both unstage a file. This confuses people because they look completely different.

#### `git restore --staged <file>` (Modern — Git 2.23+)

```bash
git restore --staged playwright-report/index.html
```

**What it does:** Removes the file from the staging area. Your changes inside the file are kept — it just won't be included in the next commit.

**When to use:** You ran `git add .` and accidentally staged a generated report, a temp file, or your real `.env`.

#### `git reset HEAD <file>` (Old syntax — same result)

```bash
git reset HEAD playwright-report/index.html
```

**What it does:** Identical to `git restore --staged`. This is the older equivalent that still works on all Git versions.

**Use `git restore --staged` on Git 2.23+.** Use `git reset HEAD` only if you're on an older Git version.

---

### 🔀 `git checkout` vs `git switch` (Switching Branches)

Both switch branches. `git switch` is the modern replacement.

```bash
# Old way — still works but does too many things (also restores files)
git checkout test/login-flow
git checkout -b test/new-feature

# New way — unambiguous, branch-only purpose (Git 2.23+)
git switch test/login-flow
git switch -c test/new-feature
```

**Recommendation:** Use `git switch` for branch operations. The old `git checkout` handles both branch switching and file restoration in one command, which causes confusion. `git switch` is only for branches — its intent is always clear.

---

### 📊 All Confusing Commands Side-by-Side

| Command | Touches Your Files? | Creates a Merge Commit? | Rewrites History? | Safe After Pushing? |
|---------|--------------------|-----------------------|------------------|---------------------|
| `git fetch` | ❌ No | ❌ No | ❌ No | ✅ Always safe |
| `git pull` | ✅ Yes | ✅ If needed | ❌ No | ✅ Always safe |
| `git merge` | ✅ Yes | ✅ Yes | ❌ No | ✅ Always safe |
| `git rebase` | ✅ Yes | ❌ No | ✅ Yes | ⚠️ Only on private branches |
| `git reset` | ✅ Yes (--hard) | ❌ No | ✅ Yes | ❌ Never after pushing |
| `git revert` | ✅ Yes | ❌ No (new commit) | ❌ No | ✅ Always safe |

## Part 7 — Undoing Mistakes

### Scenario 1 — Discard Uncommitted Changes

**When to use:** You experimented with a locator or refactored a page object, it didn't work, and you want to return to the last committed state.

```bash
# Discard changes in one specific test file
git restore tests/e2e/login.spec.ts

# Discard ALL uncommitted changes across the entire project
git restore .
```

⚠️ **Irreversible.** Changes are gone permanently once you run this.

---

### Scenario 2 — Unstage a File

**When to use:** You ran `git add .` and noticed a generated report file or temp file got staged that shouldn't be in the commit.

```bash
git restore --staged playwright-report/index.html
git restore --staged test-results/
```

Your changes in those files are kept — they just won't be in the next commit.

---

### Scenario 3 — Fix the Last Commit Message

**When to use:** You just committed with a typo or wrong message, and it has not been pushed yet.

```bash
git commit --amend -m "Add login smoke tests covering SSO and standard auth flows"
```

---

### Scenario 4 — Undo the Last Commit (Keep Changes Staged)

**When to use:** You committed too early, forgot to add a file, or want to split one commit into two smaller ones.

```bash
git reset --soft HEAD~1
# Your test files are still staged — add the missing file and re-commit
```

---

### Scenario 5 — Undo the Last Commit (Discard Everything)

**When to use:** You accidentally committed your real `.env` file with credentials, and it has not been pushed yet. You want the commit erased entirely.

```bash
git reset --hard HEAD~1
```

⚠️ **Irreversible. Only use before pushing.** If already pushed, use `git revert` instead — and also rotate your credentials immediately.

---

### Scenario 6 — Undo a Pushed Commit Safely

**When to use:** A broken test or bad config change made it into `main` and other engineers may have already pulled it.

```bash
# Find the commit hash
git log --oneline
# e.g.: a3f9c21  Add checkout tests (broken baseURL config)

# Create a new commit that reverses it
git revert a3f9c21
git push
```

---

### Scenario 7 — Stash Unfinished Work

**When to use:** You're in the middle of writing tests when your QA lead urgently asks you to fix a flaky test on `main`. You can't commit unfinished work — stash it instead.

```bash
# Save unfinished work to a temporary stack
git stash

# Switch to main, create a fix branch, fix the test
git checkout main
git pull
git checkout -b fix/login-flaky
# ... fix the flaky test ...
git add .
git commit -m "Fix flaky login test — replace hardcoded sleep with explicit network idle wait"
git push
gh pr create

# Return to your original branch and restore unfinished work
git checkout test/checkout-flow
git stash pop
# Your files are back exactly as you left them
```

## Part 8 — Team QA Collaboration Workflow

### Standard Pull Request Flow

This is how professional QA teams manage all test contributions:

```
1. Clone the test repository
2. Create a feature branch  (test/feature-name)
3. Write tests and commit with clear messages
4. Run tests locally — confirm they pass
5. Push branch to GitHub
6. Open a Pull Request
7. Teammate or QA lead reviews the tests
8. GitHub Actions runs Playwright automatically on the PR
9. Address review feedback
10. PR approved + CI green → merge to main
11. Delete the branch (local and remote)
```

### Full Example — Adding Tests for a New Feature

```bash
# 1. Start from a fresh, up-to-date main
git checkout main
git pull

# 2. Create your test branch
git checkout -b test/user-registration

# 3. Write your tests
# ... create tests/e2e/registration.spec.ts ...
# ... create pages/RegistrationPage.ts ...

# 4. Run locally — confirm they pass before pushing
npx playwright test tests/e2e/registration.spec.ts

# 5. Commit with a descriptive message
git add .
git commit -m "Add E2E tests for user registration — happy path, duplicate email, invalid inputs"

# 6. Push to GitHub
git push -u origin test/user-registration

# 7. Open a Pull Request
gh pr create \
  --title "E2E tests: user registration" \
  --body "Covers: happy path, duplicate email error, missing required fields, weak password validation"
```

### Reviewing a Teammate's PR Locally

**When to use:** You want to run a teammate's new tests on your own machine before approving their PR.

```bash
# Download and switch to their branch
gh pr checkout 42

# Run their tests
npx playwright test

# Return to your own branch when done
git checkout test/your-branch
```

### After Your PR is Merged

```bash
git checkout main
git pull
git branch -d test/user-registration              # Remove local branch
git push origin --delete test/user-registration   # Remove GitHub branch
```

## Part 9 — Professional QA Workflow & CI/CD

### What CI Does for Your Test Suite

**CI (Continuous Integration)** automatically runs your Playwright tests every time a PR is opened or code is pushed. This means:

- Tests run on every PR — no one has to remember to manually trigger them
- A failing test **blocks the PR from merging**
- Developers see results directly on GitHub within minutes of pushing
- Your `main` branch stays green and stable at all times

---

### GitHub Actions Workflow for Playwright TypeScript

Create or update `.github/workflows/playwright.yml`:

```yaml
name: Playwright Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  playwright:
    name: Run Playwright Tests
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - name: Install dependencies
        run: npm ci
        # npm ci is faster and stricter than npm install
        # It reads package-lock.json exactly and fails if it's out of sync
        # Always use npm ci in CI; use npm install locally

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test
        env:
          BASE_URL: ${{ secrets.STAGING_BASE_URL }}
          TEST_USERNAME: ${{ secrets.TEST_USERNAME }}
          TEST_PASSWORD: ${{ secrets.TEST_PASSWORD }}

      - name: Upload Playwright HTML report
        uses: actions/upload-artifact@v4
        if: always()   # Upload report even when tests fail — critical for debugging CI failures
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14
```

### Professional Best Practices

- **Never commit credentials** — use `.env` locally and GitHub Secrets in CI
- **Never commit generated output** — `test-results/`, `playwright-report/` must be in `.gitignore`
- **Run tests locally before pushing** — don't rely on CI to catch obvious failures
- **Keep PRs focused** — one feature's tests per PR is easier to review than 20 new test files at once
- **Write meaningful commit messages** — your teammates and future-you need to understand history at a glance

#### Good vs Bad Commit Messages

```bash
# ❌ Bad — tells nobody what changed or why
git commit -m "tests"
git commit -m "fix"
git commit -m "update"
git commit -m "wip2"

# ✅ Good — specific, searchable, actionable
git commit -m "Add E2E tests for checkout — happy path and failed payment scenarios"
git commit -m "Fix flaky login test — replace hardcoded sleep with explicit network idle wait"
git commit -m "Refactor ProductPage to use data-testid selectors throughout"
git commit -m "Upgrade Playwright from 1.41 to 1.42 — fix deprecated getByRole usage"
```

### 🔍 Investigating a Failing Test

**When to use:** A test suddenly fails in CI and you need to find out what changed and when.

```bash
# See recent commits — what changed recently?
git log --oneline

# See only commits that touched the failing test file
git log --oneline -- tests/e2e/login.spec.ts

# See exactly what changed in a specific commit
git show a3f9c21

# See who last modified each line (useful for pinpointing who broke a locator)
git blame tests/e2e/login.spec.ts

# Compare your branch with main to see the full diff
git diff main

# Binary search to find the exact commit that broke the test
git bisect start
git bisect bad                  # Current state: broken
git bisect good v1.5.0          # A known-good state (use a tag or commit hash)
# Git checks out a commit in the middle — you run the test:
npx playwright test tests/e2e/login.spec.ts
git bisect good     # Test passes at this commit → problem is newer
git bisect bad      # Test fails at this commit → problem is older
# Repeat until Git identifies the exact breaking commit
git bisect reset    # Exit bisect and return to your original branch
```

| `gh repo create <n> --private --source=. --remote=origin --push` | Creates a private repo on GitHub, connects it as `origin`, and pushes your local code — all in one command | When you've initialized locally with `git init` and want to push to a brand new GitHub repo in a single step |

### 📸 Staging & Committing

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git status` | Shows which files are modified (not staged), staged (ready to commit), or untracked (not yet added to Git) | Before every `git add` or `git commit` — always check what state you're in first |
| `git add .` | Stages every changed and new file in the current directory for the next commit | When you want to commit all your current changes together |
| `git add <filename>` | Stages only the specified file for the next commit | When you only want to commit a particular test file or page object, not everything |
| `git restore --staged <file>` | Removes a file from the staging area without discarding your changes to it | When you accidentally staged a generated report, `.env`, or `test-results/` and don't want it in the commit |
| `git commit -m "message"` | Permanently saves all staged changes to local history with a description | After staging the right files and you're ready to record a checkpoint in history |
| `git commit --amend -m "new msg"` | Replaces the last commit's message (and optionally adds staged changes to it) | When you just committed with a typo or forgot a file — **only before pushing** |

---

### 🔄 Pushing & Pulling

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git push` | Uploads all local commits on the current branch to GitHub | After committing, to share your tests with the team and trigger CI |
| `git push -u origin main` | Pushes `main` to GitHub and sets it as the default upstream so future pushes only need `git push` | The very first time you push the `main` branch |
| `git push -u origin <branch>` | Pushes a new branch to GitHub and sets its upstream tracking | The first time you push a new feature test branch |
| `git fetch` | Downloads the latest commits and branch info from GitHub into local Git — does **not** change your working files | Before `git rebase origin/main`; when you want to see what the team pushed without applying it yet |
| `git fetch origin` | Same as `git fetch` — explicitly names the remote for clarity | Preferred explicit form to use before rebasing |
| `git pull` | Runs `git fetch` + `git merge` in one step — downloads changes and immediately applies them to your current branch | At the start of the day on `main`; on a shared branch when you want the latest applied now |

---

### 🌿 Branching

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git branch` | Lists all local branches; `*` marks your current branch | When you need to see which branches exist or confirm which you're on |
| `git branch -a` | Lists all local branches and all remote branches that GitHub knows about | When checking if a teammate's branch exists remotely |
| `git checkout -b <name>` | Creates a new branch and switches to it immediately | Starting any new test feature, bug fix, or refactor task |
| `git switch -c <name>` | Same as `checkout -b` — the modern, clearer syntax (Git 2.23+) | Preferred on newer Git versions — unambiguously for branch creation |
| `git checkout <name>` | Switches your working directory to an existing branch | Changing to a branch that already exists |
| `git switch <name>` | Same as `checkout` for existing branches — modern preferred syntax | Preferred on newer Git versions — clearer intent |
| `git branch -d <name>` | Deletes a local branch that has already been merged | After your PR is merged and you no longer need the branch locally |
| `git branch -D <name>` | Force-deletes a local branch even if it has not been merged | When you abandon a test branch and don't intend to merge it |
| `git push origin --delete <name>` | Deletes the branch from GitHub | After merging a PR — always clean up the remote branch too |

---

### 🔀 Merging & Rebasing

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git merge <branch>` | Integrates another branch into your current branch by creating a merge commit that preserves both branches' full history | Merging an approved PR into `main`; integrating a shared branch |
| `git rebase main` | Replays your branch's commits one by one on top of the latest `main` — no merge commit, produces linear history | Updating your own private feature branch with the latest `main` before opening a PR |
| `git rebase origin/main` | Same as `git rebase main` but uses the exact remote version — use after `git fetch` | The safest form of rebase; guarantees you're rebasing on what GitHub actually has |
| `git rebase --abort` | Cancels an in-progress rebase and returns your branch to exactly how it was before you started | When a rebase hits conflicts you can't resolve right now or made a mistake starting it |
| `git rebase --continue` | Resumes the rebase after you've resolved conflicts in the current step | After editing conflicting files and running `git add` on the resolved files |

### ↩️ Undoing Mistakes

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git restore .` | Discards **all** uncommitted changes in every file — resets the entire working directory to the last commit | When your experiment completely failed and you want a clean slate — **irreversible** |
| `git restore <file>` | Discards uncommitted changes in one specific file only | When only one test file has changes you want to throw away |
| `git restore --staged <file>` | Removes a file from the staging area while keeping your changes to the file intact | When you accidentally staged a generated file, a temp file, or your real `.env` |
| `git reset --soft HEAD~1` | Undoes the last commit but keeps all its changes staged and ready to re-commit | When you committed too early, need to add something, or want to rewrite the message |
| `git reset --hard HEAD~1` | Undoes the last commit and permanently deletes all the changes it contained | When the last commit was completely wrong and **has not been pushed** — **irreversible** |
| `git revert <commit-hash>` | Creates a new commit that reverses the effect of a specific previous commit, leaving all history intact | When a bad commit has already been pushed to GitHub and others may have pulled it — the only safe undo after pushing |
| `git commit --amend -m "msg"` | Replaces the last commit's message, or adds currently staged files to the last commit | Fixing a typo in a message or adding a file you forgot — **only before pushing** |

---

### 📦 Stashing

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git stash` | Saves all uncommitted changes (staged and unstaged) to a temporary stack and cleans your working directory | When you need to urgently switch branches but aren't ready to commit your in-progress test work |
| `git stash pop` | Restores the most recently stashed changes and removes them from the stash list | After you finish the urgent task and return to your original branch |
| `git stash list` | Shows all saved stashes with their index numbers and the branch they were stashed on | When you've stashed multiple times and need to see what's saved |
| `git stash apply stash@{0}` | Applies a specific stash's changes without removing it from the stash list | When you want to apply the same stashed changes to more than one branch |
| `git stash clear` | Permanently deletes all saved stashes | When you no longer need any of the stashed work |

### 🔍 Inspecting & History

| Command | What It Does | When to Use |
|---------|-------------|-------------|
| `git log` | Shows the full commit history with author name, date, and complete message | When you need detailed information about past commits |
| `git log --oneline` | Shows one compact line per commit (hash + message) | Quick scan of recent changes; locating a specific commit hash |
| `git log --oneline --graph --all` | Shows a visual ASCII tree of all branches and their commits alongside the history | Understanding how branches diverged from and merged back into each other |
| `git log --oneline -- <file>` | Shows only the commits that modified a specific file | Finding when a particular test file was last changed or who touched it |
| `git diff` | Shows line-by-line changes in your working directory that have not been staged yet | Before `git add` — reviewing exactly what you changed before staging |
| `git diff --staged` | Shows line-by-line changes that are staged and will be included in the next commit | After `git add` — confirming what your next commit will contain |
| `git show <commit-hash>` | Shows the full details of a specific commit including all file diffs | Investigating what a specific past commit changed |
| `git blame <file>` | Annotates each line of a file with the commit hash and author who last changed it | Finding who introduced a specific locator, selector, or assertion — essential for flaky test investigation |
| `git bisect start` | Begins an automated binary search through commit history to find the commit that introduced a problem | When tests were passing at some point and failing now, and you need to pinpoint the exact breaking commit efficiently |
| `git bisect good` | Marks the currently checked-out commit as passing during a bisect session | Tell Git this commit is before the problem — it will check out a newer one next |
| `git bisect bad` | Marks the currently checked-out commit as failing during a bisect session | Tell Git this commit has the problem — it will check out an older one next |
| `git bisect reset` | Ends the bisect session and returns you to your original branch | After bisect has identified the culprit commit |

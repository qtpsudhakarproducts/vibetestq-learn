## 1. What Is Git?

Git is a **distributed version control system** — a tool that tracks every change made to files in a project over time. It records who made each change, when it was made, and what exactly changed. It also allows multiple people to work on the same project simultaneously without overwriting each other's work.

The word **distributed** is important. Unlike older version control systems (like SVN) where the full project history only lived on one central server, with Git every developer's computer holds a **complete copy of the entire history**. You can work offline, make commits, view history, and switch branches — all without any network connection. The server (GitHub) is just another copy of the repository that everyone synchronizes with.

### Why Test Automation Engineers Need Git

Test automation code is software. It has the same version control needs as application code:

- You need to **track changes** — knowing what changed in your test suite between last week and today
- You need to **collaborate** — multiple engineers contributing to the same automation framework
- You need to **isolate work** — developing a new test for a feature without breaking the existing test suite
- You need to **review code** — catching bugs in test logic before they reach the main branch
- You need to **integrate with CI/CD** — Playwright tests are typically triggered by Git events (a push, a pull request)
- You need to **roll back** — reverting a bad change to the test suite that is causing false failures

### What Git Tracks

Git tracks changes to **text files** with full precision — it records exactly which lines changed, what the old content was, and what the new content is. For binary files (images, compiled binaries), Git can store them but cannot show meaningful diffs.

In a Playwright project, Git will track:
- All `.ts` / `.js` test files
- `playwright.config.ts`
- `package.json` and `package-lock.json`
- `.github/workflows/*.yml` (CI pipeline definitions)
- `README.md` and documentation
- Auth state files (if checked in — though usually they should be in `.gitignore`)

### What Git Does NOT Track (by default)

- `node_modules/` — regenerated from `package.json` via `npm install`
- `test-results/` — generated by Playwright at runtime
- `playwright-report/` — generated reports
- `.env` files — containing secrets and API keys
- `auth/*.json` — saved auth state containing real session tokens

These are excluded using a `.gitignore` file.

> 💡 **Mental Model:** Git is like a detailed journal for your project. Every commit is a dated journal entry that records exactly what changed. You can flip back to any entry and see (or restore) the project exactly as it was at that moment.

## 2. Core Git Concepts

Before running a single command, these concepts need to be understood clearly. Almost every Git problem — and every Git command — connects back to one of these.

### The Three Areas

Git manages your files across three distinct areas. Understanding these three areas explains why Git commands behave the way they do:

```
Working Directory    →    Staging Area (Index)    →    Repository (.git)
  (your files)              (prepared changes)           (committed history)

  git add ──────────────────────►
                       git commit ─────────────────────►
  git checkout ◄──────────────────────────────────────── (restore files)
```

**Working Directory** is your project folder — the files you see and edit in VS Code or your terminal. Changes here are not tracked yet.

**Staging Area (Index)** is a preparation zone. Before committing, you explicitly choose which changes to include by staging them with `git add`. This lets you commit only part of your working directory changes if needed.

**Repository** is the permanent record stored in the hidden `.git` folder. Once a change is committed it is permanently recorded in the project history.

### Commits

A **commit** is a snapshot of all tracked files at a specific moment in time. Every commit has:

- A **hash** (SHA-1) — a 40-character unique identifier like `a3f8c2d1...`
- An **author** — name and email of who made the commit
- A **timestamp** — exact date and time
- A **message** — a human-readable description of what changed
- A **parent** — a reference to the previous commit (forming a chain of history)

```
commit a3f8c2d
Author: Jane Smith <jane@example.com>
Date:   Mon Jan 20 14:32:00 2025

    Add login page tests for invalid credentials

    - Test empty username scenario
    - Test empty password scenario
    - Test SQL injection attempt
```

Commits are **immutable** — once made, a commit never changes. Operations that appear to "edit" a commit (like `--amend` or `rebase`) actually create a new commit and discard the reference to the old one.

### Branches

A **branch** is a lightweight pointer to a specific commit. It moves forward automatically with each new commit you make on it.

```
main:    A ── B ── C ── D  ← (HEAD)
                    \
feature:             E ── F  ← (HEAD of feature branch)
```

Branches are what allow parallel development. One engineer works on `feature/login-tests` while another works on `fix/payment-flakiness` — both branching from `main` at different points, developing independently, and merging back when done.

The default branch is typically called `main` (older repositories may use `master`).

### HEAD

`HEAD` is a special pointer that tells Git **where you currently are** in the project history. It usually points to the tip of your current branch:

```
HEAD → main → commit D
```

When you switch branches, HEAD moves to point at the new branch. When you make a new commit, HEAD and the branch pointer both advance to the new commit.

A "detached HEAD" state occurs when HEAD points directly to a commit instead of a branch — this happens when you check out a specific commit hash. You can look around but should not commit in this state without creating a branch first.

### Tags

A **tag** is a permanent label attached to a specific commit. Unlike branches which move with new commits, tags never move. They are used to mark release points:

```
git tag v1.0.0          # tag the current commit
git tag v1.0.0 a3f8c2d  # tag a specific commit
```

### The `.git` Directory

When you run `git init` or `git clone`, Git creates a hidden `.git` directory inside your project. This directory IS the repository — it contains the entire commit history, all branches, all tags, and all configuration. Deleting `.git` would leave you with just the working files and no version history.

## 3. Working With Repositories

### Initializing a New Repository

```bash
# Create a new git repository in the current directory
git init

# Create and initialize in a new directory
git init my-playwright-project
```

This creates the `.git` folder. The directory is now a Git repository, but it has no commits yet.

### Cloning an Existing Repository

```bash
# Clone from GitHub (creates a local copy with full history)
git clone https://github.com/org/playwright-tests.git

# Clone into a specific folder name
git clone https://github.com/org/playwright-tests.git my-tests

# Clone with SSH (requires SSH key setup)
git clone git@github.com:org/playwright-tests.git
```

Cloning downloads the full repository history, sets up a remote called `origin` pointing back to the source, and checks out the default branch.

### Checking Status

```bash
git status
```

This is the most useful command to run constantly. It shows:
- Which files have been modified in the working directory
- Which files are staged (ready to commit)
- Which files are untracked (new files Git does not know about yet)
- Whether your branch is ahead or behind the remote

```
On branch feature/add-login-tests
Your branch is up to date with 'origin/feature/add-login-tests'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        new file:   tests/login.spec.ts

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
        modified:   playwright.config.ts

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        tests/helpers/auth.ts
```

### Staging Changes

```bash
# Stage a specific file
git add tests/login.spec.ts

# Stage multiple files
git add tests/login.spec.ts tests/helpers/auth.ts

# Stage all changes in current directory
git add .

# Stage parts of a file interactively (chunk by chunk)
git add -p playwright.config.ts
```

`git add .` is convenient but use it carefully — it stages everything including files you might not want to commit (test results, temporary files). Always run `git status` after staging to confirm what is about to be committed.

### Committing

```bash
# Commit with a message
git commit -m "Add login page tests for invalid credential scenarios"

# Stage all tracked files and commit in one step
git commit -am "Fix flaky selector in payment test"

# Open the default editor to write a longer commit message
git commit
```

#### Writing Good Commit Messages

A good commit message is important in a team environment because it forms the project's history. The convention is:

```
Short summary line (max 72 characters, imperative mood)

Longer body explaining WHY the change was made, not WHAT
(the diff already shows what changed). Wrap at 72 characters.

- Use bullet points for multiple items
- Reference issue numbers: Closes #42
```

Good messages use the **imperative mood** — "Add tests" not "Added tests" or "Adding tests". Think of it as completing the sentence: "If applied, this commit will... **Add tests for the login page**."

Examples for a test automation engineer:

```
✅ Add tests for login with invalid credentials
✅ Fix flaky selector in checkout flow — use getByRole instead of CSS
✅ Refactor page object model for user profile page
✅ Skip payment tests on Firefox pending bug #1234
❌ Fixed stuff
❌ WIP
❌ asdfg
```

### Viewing History

```bash
# Full commit log
git log

# Compact one-line format
git log --oneline

# Graph view showing branches and merges
git log --oneline --graph --all

# History of a specific file
git log --oneline tests/login.spec.ts

# Who changed each line of a file
git blame tests/login.spec.ts

# Show changes introduced by a specific commit
git show a3f8c2d
```

### Viewing Differences

```bash
# What changed in the working directory (not staged yet)
git diff

# What is staged and ready to commit
git diff --staged

# Difference between two branches
git diff main feature/login-tests

# Difference between two commits
git diff a3f8c2d b7e9a1f
```

### The .gitignore File

`.gitignore` tells Git which files and folders to never track. For a Playwright project it should contain:

```gitignore
# Dependencies
node_modules/

# Playwright output
test-results/
playwright-report/
blob-report/
.playwright/

# Auth state (contains real session tokens — never commit these)
auth/
**/storageState.json

# Environment variables
.env
.env.local
.env.*.local

# OS files
.DS_Store
Thumbs.db

# Editor files
.vscode/settings.json
.idea/
```

Once a file is listed in `.gitignore`, Git will completely ignore it — it will not show up in `git status` and cannot be accidentally staged.

> ⚠️ **Important:** If a file was already committed before being added to `.gitignore`, Git will continue to track it. You must explicitly remove it from tracking: `git rm --cached filename`

## 4. Joining a Project Mid-Way — Starting From an Existing GitHub Repo

This is one of the most common real-world scenarios for a test automation engineer: you join a team, the automation framework already exists on GitHub, and you need to get it running on your machine from scratch. You have no local repository. The flow starts entirely from GitHub.

This section covers every step for **Windows, macOS, and Linux** because the commands and tools differ meaningfully between operating systems. Read the section for your OS at each step.

---

### Which Terminal to Use

Before anything else, know which terminal you are working in — this affects every command in this section.

| OS | Recommended Terminal | Notes |
|---|---|---|
| **Windows** | **Git Bash** (installed with Git for Windows) | Gives you a Unix-like shell with `ls`, `cat`, `ssh-keygen`, etc. Use this for all Git work |
| **Windows** | PowerShell | Works for Git commands but some Unix commands differ — noted where relevant |
| **Windows** | Command Prompt (cmd) | Not recommended — missing many Unix tools Git setup relies on |
| **macOS** | Terminal (built-in) or iTerm2 | zsh is the default shell since macOS Catalina |
| **Linux** | Terminal / Bash | Bash or zsh depending on distro |

> 💡 **Windows users:** Install Git for Windows from https://git-scm.com/download/win — this installs Git Bash alongside Git. Use Git Bash for everything in this section unless otherwise noted.

### The Full Flow at a Glance

```
GitHub Repo (exists)
  │
  ├── 1. Get access to the repository
```

### Step 1 — Get Access to the Repository

Before you can clone, you need permission. GitHub repositories can be public (anyone can clone) or private (requires explicit access).

**What to ask your team lead or onboarding contact:**
- The repository URL (e.g. `https://github.com/org-name/playwright-tests`)
- An invite to the GitHub organisation or direct collaborator access to the repo
- Which team or role to be added under (read, write, or admin access)
- Which branch is the main working branch (usually `main` but sometimes `develop` or `qa`)
- Whether there is an onboarding doc or README to read first
- Where environment variable values are stored (password manager, internal wiki, Slack channel)

**How to verify you have access:**
- Go to the repository URL in your browser while logged into GitHub
- If you can see the code and file list, you have at least read access
- If you see a 404 or "This repository could not be found", you have not been added yet — follow up before proceeding

### Step 3 — Configure Git Identity

This must be done before making any commits. Git uses this information to tag every commit you make with your name and email.

**All OS — the commands are identical:**
```bash
git config --global user.name "Your Full Name"
git config --global user.email "you@yourcompany.com"
```

> ⚠️ Use the **same email address** registered with your GitHub account. If they do not match, your commits will not link to your GitHub profile — your contributions will appear as an unknown user in pull requests and the commit log.

**Set your preferred editor:**

```bash
# VS Code (recommended — works on all OS if VS Code is installed)
git config --global core.editor "code --wait"

# Windows — Notepad as fallback
git config --global core.editor "notepad"

# macOS — nano as fallback
git config --global core.editor "nano"

# Linux — nano or vim
git config --global core.editor "nano"
```

**Set the default branch name:**
```bash
git config --global init.defaultBranch main
```

**Windows only — configure line ending handling:**

Windows uses `\r\n` (CRLF) for line endings. macOS and Linux use `\n` (LF). Without this setting, Git on Windows may add or remove line endings on every file, producing noisy diffs.

```bash
# Windows — convert CRLF to LF on commit, restore CRLF on checkout
git config --global core.autocrlf true
```

macOS and Linux do not need this — their default (`input`) is already correct.

**Verify all configuration:**
```bash
git config --list
```

### Step 4 — Set Up Authentication

You need to authenticate with GitHub when pushing and pulling. There are two methods. SSH is recommended for daily use; HTTPS with a PAT is the fallback for environments where SSH is blocked.

---

#### Option A — SSH Key (Recommended)

SSH uses a key pair — a private key that stays on your machine and a public key that you register on GitHub. Once set up, you are never prompted for a password.

##### Why the key is generated on your machine, not on GitHub

This is an important concept to understand clearly.

GitHub does allow you to generate SSH keys on their side and download the private key — but **this is not how personal developer authentication should work**, and it is not recommended.

The entire security model of SSH is built on one rule:

> **The private key is generated on your machine, stays on your machine, and never travels anywhere.**

Here is why:

- When you generate the key pair locally, the private key never leaves your machine. GitHub only ever sees the public key, which is mathematically useless without its matching private key.
- If you generate the key on GitHub and download it, the private key travels over the internet. If anyone intercepts that download, or if the file is accidentally shared or committed to a repository, your access is fully compromised.
- The public key is designed to be shared freely — it cannot be used to impersonate you. The private key is the secret — it must never be shared or transmitted.

**The correct flow:**

```
Your machine                          GitHub
─────────────────────────────────     ──────────────────────────
ssh-keygen generates:
  private key  → stays here only
  public key   ──────────────────────→ uploaded to GitHub Settings
                                        GitHub stores public key
                                        and uses it to verify you
```

**When would you generate on GitHub instead?**

GitHub's key generation on their side is intended for specific scenarios — such as **deploy keys** for CI/CD pipelines or server automation where a machine needs access to a repository but cannot interactively generate its own key. It is not for personal developer use.

For day-to-day work as a developer or test automation engineer, always generate the key pair on your own machine.

##### Check if you already have an SSH key

**macOS / Linux / Git Bash on Windows:**
```bash
ls ~/.ssh
# Look for: id_ed25519 and id_ed25519.pub
# Older keys may be named: id_rsa and id_rsa.pub
```

**Windows PowerShell:**
```powershell
ls $env:USERPROFILE\.ssh
```

If these files exist, you already have a key — skip to the "Add key to SSH agent" step.

##### Generate a new SSH key pair

**macOS / Linux / Git Bash on Windows:**
```bash
ssh-keygen -t ed25519 -C "you@yourcompany.com"
# When prompted for file location — press Enter to accept the default
# When prompted for a passphrase — enter one (recommended) or press Enter to skip
```

The default saves to:
- macOS / Linux: `~/.ssh/id_ed25519`
- Windows (Git Bash): `C:\Users\YourName\.ssh\id_ed25519`

**Windows PowerShell (if not using Git Bash):**
```powershell
ssh-keygen -t ed25519 -C "you@yourcompany.com"
# Default saves to: C:\Users\YourName\.ssh\id_ed25519
```

##### Add the key to the SSH agent

The SSH agent holds your key in memory so you are not prompted for the passphrase on every operation.

**macOS:**
```bash
# Start the agent (usually already running on macOS)
eval "$(ssh-agent -s)"

# Add the key
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
# --apple-use-keychain stores the passphrase in macOS Keychain automatically
```

Add this to `~/.ssh/config` to make the agent remember across reboots:
```
Host github.com
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519
```

**Linux:**
```bash
# Start the agent
eval "$(ssh-agent -s)"

# Add the key
ssh-add ~/.ssh/id_ed25519

# To persist across reboots, add to ~/.bashrc or ~/.zshrc:
# eval "$(ssh-agent -s)"
# ssh-add ~/.ssh/id_ed25519
```

**Windows (Git Bash):**
```bash
# Start the agent
eval "$(ssh-agent -s)"

# Add the key
ssh-add ~/.ssh/id_ed25519
```

**Windows (PowerShell) — enable the OpenSSH Authentication Agent service:**
```powershell
# Run PowerShell as Administrator
Set-Service -Name ssh-agent -StartupType Automatic
Start-Service ssh-agent

# Add the key
ssh-add $env:USERPROFILE\.ssh\id_ed25519
```

##### Copy your public key

**macOS:**
```bash
pbcopy < ~/.ssh/id_ed25519.pub
# Key is now in your clipboard
```

**Linux:**
```bash
# If xclip is installed
xclip -selection clipboard < ~/.ssh/id_ed25519.pub

# If xsel is installed
xsel --clipboard --input < ~/.ssh/id_ed25519.pub

# Or just print it and copy manually
cat ~/.ssh/id_ed25519.pub
```

**Windows (Git Bash):**
```bash
cat ~/.ssh/id_ed25519.pub | clip
```

**Windows (PowerShell):**
```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub | Set-Clipboard
```

##### Add the public key to GitHub

1. Go to GitHub → click your profile picture (top right) → **Settings**
2. In the left sidebar → **SSH and GPG keys** → **New SSH key**
3. Title: give it a descriptive name like `Work Windows Laptop` or `Personal MacBook`
4. Key type: leave as **Authentication Key**
5. Paste your public key into the **Key** field
6. Click **Add SSH key**

##### Test the SSH connection

**All OS:**
```bash
ssh -T git@github.com
```

Expected response:
```
Hi your-username! You've successfully authenticated, but GitHub does not provide shell access.
```

If you see this message, SSH is fully configured. If you get a `Permission denied` error, revisit the steps above — the most common cause is the public key not being saved to GitHub correctly.

---

#### Option B — HTTPS with Personal Access Token (PAT)

Use this if SSH is blocked by your corporate network or firewall.

##### Create a PAT on GitHub

1. Go to GitHub → Settings → **Developer settings** → **Personal access tokens** → **Tokens (classic)**
2. Click **Generate new token (classic)**
3. Give it a descriptive name: `Work laptop — Playwright automation`
4. Set an expiry: 90 days is a reasonable balance of security and convenience
5. Select scopes: check **`repo`** (gives full access to repositories)
6. Click **Generate token**
7. **Copy the token immediately** — GitHub only shows it once. Store it in your password manager.

##### Clone and authenticate

When Git asks for credentials, use your GitHub username and the PAT as the password:

```bash
git clone https://github.com/org/playwright-tests.git
# Username: your-github-username
# Password: ghp_xxxxxxxxxxxx   ← the PAT, not your GitHub account password
```

##### Store credentials so you are not asked every time

**macOS:**
```bash
git config --global credential.helper osxkeychain
```
macOS Keychain stores the PAT securely after the first successful authentication.

**Windows:**
```bash
git config --global credential.helper manager
```
Windows Credential Manager stores the PAT. This is set automatically when Git for Windows is installed.

**Linux:**
```bash
# Cache in memory for 8 hours (28800 seconds)
git config --global credential.helper 'cache --timeout=28800'

# Or store permanently on disk (less secure but convenient)
git config --global credential.helper store
# Warning: store saves credentials in plain text at ~/.git-credentials
```

After the first successful push or pull with the PAT, credentials are stored and you will not be prompted again until the token expires.

### Step 5 — Clone the Repository

Cloning downloads the complete repository — all files, all branches, and the full commit history — to your local machine.

**Get the clone URL from GitHub:**
- Go to the repository on GitHub
- Click the green **Code** button
- Select the **SSH** tab if you configured SSH, or the **HTTPS** tab for PAT authentication
- Copy the URL

**All OS — clone commands are identical:**
```bash
# Clone using SSH (if SSH is configured)
git clone git@github.com:org-name/playwright-tests.git

# Clone using HTTPS (if using PAT)
git clone https://github.com/org-name/playwright-tests.git

# Clone into a custom folder name
git clone git@github.com:org-name/playwright-tests.git my-automation-project
```

**Navigate into the project:**

macOS / Linux / Git Bash:
```bash
cd playwright-tests
```

Windows PowerShell:
```powershell
cd playwright-tests
# or
Set-Location playwright-tests
```

**Verify the clone worked correctly:**
```bash
# Confirm the remote is set up
git remote -v
# origin  git@github.com:org-name/playwright-tests.git (fetch)
# origin  git@github.com:org-name/playwright-tests.git (push)

# Confirm you are on the right branch
git status
# On branch main
# Your branch is up to date with 'origin/main'.

# See all branches including remote ones
git branch -a
```

### Step 6 — Understand the Repository Structure

### Step 7 — Install Dependencies

The repository tracks `package.json` but not `node_modules/` — that folder is in `.gitignore` and must be regenerated on every machine.

**All OS — npm commands are identical:**
```bash
# Install exact versions from package-lock.json (recommended for team projects)
npm ci

# Or install from package.json (may update minor/patch versions)
npm install
```

**`npm install` vs `npm ci`:**

| `npm install` | `npm ci` |
|---|---|
| May update `package-lock.json` | Never modifies `package-lock.json` |
| May install newer patch versions | Installs the exact locked versions |
| Works even if lock file is missing | Fails if lock file is missing or out of sync |
| Good for personal development | Correct choice for joining a team project |

Always use `npm ci` when cloning a team project — it guarantees you have the same dependency versions as every other engineer and the CI pipeline.

**Install Playwright browsers:**

Playwright downloads its own browser binaries separately from `node_modules`. The location of these binaries differs by OS:

| OS | Default browser cache location |
|---|---|
| Windows | `%USERPROFILE%\AppData\Local\ms-playwright` |
| macOS | `~/Library/Caches/ms-playwright` |
| Linux | `~/.cache/ms-playwright` |

```bash
# Install all browsers + system dependencies (recommended first time)
npx playwright install --with-deps

# Install only specific browsers
npx playwright install chromium --with-deps
npx playwright install chromium firefox --with-deps
```

**What `--with-deps` does per OS:**

- **Linux** — installs system packages (fonts, shared libraries like `libglib`, `libnss`, media codecs) that the browsers need. Without this, browsers fail to launch with errors like `error while loading shared libraries`. This flag is essential on Linux.
- **macOS** — installs minimal dependencies; browsers generally work without this flag on macOS but it is safe to include
- **Windows** — installs Visual C++ redistributables and media codecs if missing

> ⚠️ **Linux users:** Never skip `--with-deps` on a fresh Linux machine. The error messages when dependencies are missing are cryptic and do not point back to Playwright installation as the cause.

**Verify everything is installed:**
```bash
npx playwright --version
# e.g. Version 1.44.0
```

## 5. Branching and Merging

Branching is where Git's power for team collaboration becomes real. Every feature, bug fix, or experiment should live on its own branch.

### Creating and Switching Branches

```bash
# Create a new branch
git branch feature/login-tests

# Switch to an existing branch
git checkout feature/login-tests

# Create AND switch in one command (preferred)
git checkout -b feature/login-tests

# Modern syntax (Git 2.23+)
git switch -c feature/login-tests

# List all branches (local)
git branch

# List all branches including remote
git branch -a
```

### Branch Naming Conventions

Good branch names describe what the branch is for. Common conventions for test automation:

```
feature/add-checkout-tests
feature/login-page-pom
fix/flaky-payment-test
fix/timeout-in-firefox
chore/upgrade-playwright-to-1-44
test/add-mobile-viewport-coverage
refactor/auth-helper-cleanup
```

Avoid spaces (use hyphens), avoid vague names (`my-branch`, `test2`, `new`), and keep them short enough to read at a glance.

### Merging

Merging combines the work from one branch into another. There are two types of merges:

**Fast-forward merge** — happens when the target branch has not moved since the feature branch was created. Git simply moves the pointer forward:

```
Before:
  main:    A ── B ── C
                      \
  feature:             D ── E

After fast-forward merge:
  main:    A ── B ── C ── D ── E
```

```bash
git checkout main
git merge feature/login-tests   # fast-forward if possible
```

**Three-way merge** — happens when both branches have new commits. Git creates a new merge commit that combines both histories:

```
Before:
  main:    A ── B ── C ── F
                      \
  feature:             D ── E

After three-way merge:
  main:    A ── B ── C ── F ── M (merge commit)
                      \       /
  feature:             D ── E
```

```bash
git checkout main
git merge --no-ff feature/login-tests   # force a merge commit even if fast-forward is possible
```

### Merge Conflicts

A **conflict** occurs when two branches changed the same lines of the same file in different ways. Git cannot automatically decide which version is correct and asks you to resolve it manually.

A conflicted file looks like this:

```
<<<<<<< HEAD (main branch version)
await page.getByRole('button', { name: 'Submit' }).click();
=======
await page.locator('#submit-btn').click();
>>>>>>> feature/login-tests (incoming version)
```

To resolve:
1. Open the conflicted file
2. Choose which version to keep (or combine both)
3. Remove the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`)
4. Stage the resolved file: `git add tests/login.spec.ts`
5. Complete the merge: `git commit`

### Rebasing

Rebasing is an alternative to merging. Instead of creating a merge commit, rebase **replays** your commits on top of the target branch, producing a linear history:

```
Before:
  main:    A ── B ── C ── F
                      \
  feature:             D ── E

After rebase of feature onto main:
  main:    A ── B ── C ── F
                           \
  feature:                  D' ── E'  (new commits, replayed on top of F)
```

```bash
git checkout feature/login-tests
git rebase main
```

**When to merge vs. rebase:**

| Scenario | Use |
|---|---|
| Merging a completed feature branch into main | `merge` — preserves branch history |
| Keeping a feature branch up to date with main | `rebase` — cleaner, linear history |
| Working on a shared branch with other people | `merge` — rebasing shared branches rewrites history, causing problems for others |
| Solo branch, want a clean history | `rebase` |

> ⚠️ **Golden Rule:** Never rebase a branch that other people are working on. Rebasing rewrites commit hashes — anyone who based work on the old commits will have a corrupted history.

### Deleting Branches

```bash
# Delete a branch that has been merged
git branch -d feature/login-tests

# Force delete an unmerged branch
git branch -D feature/login-tests

# Delete a remote branch
git push origin --delete feature/login-tests
```

## 6. Remote Repositories and GitHub

A **remote** is a version of your repository hosted somewhere else — typically on GitHub. It allows team members to share work by pushing to and pulling from the same remote.

### Remote Commands

```bash
# List remotes
git remote -v

# Add a remote (done automatically when you clone)
git remote add origin https://github.com/org/playwright-tests.git

# Change a remote URL
git remote set-url origin git@github.com:org/playwright-tests.git
```

The remote is conventionally named `origin` — this is just a name, not a special keyword.

### Fetching, Pulling and Pushing

```bash
# Fetch — download remote changes without applying them
# (updates remote-tracking branches like origin/main)
git fetch origin

# Pull — fetch + merge into current branch
git pull origin main

# Pull with rebase instead of merge
git pull --rebase origin main

# Push your branch to the remote
git push origin feature/login-tests

# Push and set upstream (so future git push works without arguments)
git push -u origin feature/login-tests

# Push all local branches
git push --all origin
```

### The Difference Between Fetch and Pull

This confuses many beginners.

`git fetch` downloads the latest commits from the remote and updates the remote-tracking branches (`origin/main`, `origin/feature-x`) but **does not change your local files or current branch**. It is safe to run at any time.

`git pull` does a `git fetch` followed immediately by a `git merge` (or `git rebase` with `--rebase`). It updates your current branch with the downloaded changes.

The professional habit is to `git fetch` first, review what changed with `git log origin/main..main`, and then `git merge` or `git rebase` deliberately rather than using `git pull` blindly.

### Tracking Branches

When you push a branch with `-u`, Git sets up a **tracking relationship** between your local branch and the remote branch. After this:

```bash
git push    # automatically knows to push to origin/feature/login-tests
git pull    # automatically knows to pull from origin/feature/login-tests
git status  # shows "Your branch is 2 commits ahead of 'origin/feature/login-tests'"
```

## 7. What Is GitHub?

GitHub is a **web-based platform** built on top of Git. While Git is the version control tool that runs on your local machine, GitHub is the remote hosting service that stores your repositories and adds collaboration features on top of them.

Git can exist without GitHub — you can use any server or even just local repositories. But GitHub (and similar platforms like GitLab and Bitbucket) adds:

- A web UI to browse code, history, and diffs
- **Pull Requests** — the core collaboration workflow
- **Issues** — bug tracking and feature requests
- **Actions** — CI/CD pipelines triggered by Git events
- **Branch protection rules** — preventing direct pushes to main
- **Code review tools** — inline comments on specific lines of code
- **Repository settings** — access control, webhooks, secrets

### GitHub vs. Git — The Distinction

| Git | GitHub |
|---|---|
| Command-line tool | Web platform |
| Runs on your machine | Runs on GitHub's servers |
| Free and open source | Commercial service (free tier available) |
| Works offline | Requires internet |
| Manages version history | Manages collaboration + CI/CD |
| Knows nothing about pull requests | Pull requests are a GitHub concept |

> 💡 **Mental Model:** Git is the engine. GitHub is the car body built around it — the dashboard, doors, and steering wheel that make the engine usable for a team.

### GitHub Authentication

Two methods for authenticating with GitHub from your terminal:

**HTTPS with Personal Access Token (PAT):**
```bash
# When you push, GitHub prompts for credentials
# Use your GitHub username and a PAT (not your account password)
git push origin main
# Username: your-github-username
# Password: ghp_xxxxxxxxxxxx  ← PAT, not your password
```

**SSH Key (recommended for regular use):**
```bash
# Generate an SSH key pair
ssh-keygen -t ed25519 -C "your-email@example.com"

# Add the public key to GitHub → Settings → SSH Keys
cat ~/.ssh/id_ed25519.pub

# Test the connection
ssh -T git@github.com

# Use SSH remote URL
git remote set-url origin git@github.com:org/repo.git
```

SSH is preferred for daily use because it never requires re-entering credentials once set up.

## 8. GitHub Workflows for Test Automation Engineers

This section covers how test automation engineers work with GitHub day-to-day — not just storing code, but using GitHub's features to collaborate, review, and integrate with CI.

### The Feature Branch Workflow (Standard Team Workflow)

This is the most common workflow in professional teams:

```
1. Pull latest main
2. Create a feature branch
3. Make commits on the branch
4. Push the branch to GitHub
5. Open a Pull Request
6. Get code review + CI passes
7. Merge into main
8. Delete the branch
```

```bash
# 1. Start from an up-to-date main
git checkout main
git pull origin main

# 2. Create your branch
git checkout -b feature/add-checkout-tests

# 3. Do your work and commit
git add tests/checkout.spec.ts
git commit -m "Add checkout flow tests for guest user"

git add tests/checkout.spec.ts
git commit -m "Add checkout tests for registered user with saved address"

# 4. Push to GitHub
git push -u origin feature/add-checkout-tests

# 5. Open a Pull Request on GitHub (via web UI or GitHub CLI)
gh pr create --title "Add checkout flow tests" --body "Covers guest and registered user flows"

# 6. After review and CI passes — merge on GitHub
# 7. Clean up locally
git checkout main
git pull origin main
git branch -d feature/add-checkout-tests
```

### Pull Requests (PRs)

A **Pull Request** is a GitHub feature that proposes merging one branch into another. It is the central collaboration mechanism for professional teams.

When you open a PR, GitHub shows:
- A diff of every file changed between the source branch and the target branch
- A status of all CI checks (Playwright tests, linting, type-checking)
- A space for reviewers to leave comments on specific lines
- A conversation thread for discussion
- A merge button (enabled only when all required checks pass and reviews are approved)

**What a good PR looks like for a test automation engineer:**

```
Title: Add login page tests for invalid credential scenarios

Description:
## What this PR does
- Adds tests for empty username, empty password, and invalid combination
- Adds tests for account lockout after 5 failed attempts
- Uses POM pattern — LoginPage object added to pages/

## How to test
npx playwright test tests/login.spec.ts

## Related issue
Closes #42
```

### Branch Protection Rules

In a professional team, the `main` branch should be protected. GitHub allows you to configure:

- **Require pull request before merging** — no one can push directly to main
- **Require status checks to pass** — Playwright CI must be green before merge is allowed
- **Require approvals** — at least 1 or 2 reviewers must approve the PR
- **Dismiss stale reviews** — if new commits are pushed after approval, approval is cleared

These rules prevent broken tests from landing in main and ensure all code is reviewed.

### GitHub Actions for Playwright

GitHub Actions is GitHub's built-in CI/CD system. It runs your Playwright tests automatically on every push and pull request.

A typical Playwright workflow file (`.github/workflows/playwright.yml`):

```yaml
name: Playwright Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30
```

This workflow:
- Triggers on every push to `main` and every PR targeting `main`
- Runs on a fresh Ubuntu Linux VM
- Installs Node, dependencies, and Playwright browsers
- Runs all tests
- Uploads the HTML report as an artifact (downloadable from the Actions tab even if the run fails)

### GitHub Secrets for Test Automation

Test automation often needs credentials — test user passwords, API keys, base URLs for staging environments. These should never be committed to the repository. Store them as GitHub Secrets:

1. Go to repository → Settings → Secrets and variables → Actions
2. Add secrets (e.g., `TEST_USER_PASSWORD`, `STAGING_BASE_URL`)
3. Reference them in your workflow:

```yaml
- name: Run Playwright tests
  run: npx playwright test
  env:
    BASE_URL: ${{ secrets.STAGING_BASE_URL }}
    TEST_PASSWORD: ${{ secrets.TEST_USER_PASSWORD }}
```

Access in your tests:
```ts
const baseURL = process.env.BASE_URL ?? 'https://localhost:3000';
```

### Reviewing Code on GitHub

When reviewing a PR from a teammate:

- **Leave inline comments** by clicking the `+` next to any line in the diff
- Use **suggestion blocks** to propose exact code changes the author can accept with one click:
  ````
  ```suggestion

  ````
- Mark your review as **Approve**, **Request changes**, or **Comment**
- Check that CI is passing before approving

## 9. What Is GitSH?

**GitSH** (also written as `gitsh`) is an **interactive shell specifically designed for running Git commands**. Instead of prefixing every command with `git`, you open the gitsh shell and type commands directly.

### The Problem GitSH Solves

In a normal terminal session, when you are doing a lot of Git work, every command starts with `git`:

```bash
git status
git add tests/login.spec.ts
git commit -m "Add tests"
git push origin feature/login-tests
git log --oneline
git diff main
git stash
git stash pop
```

Typing `git` dozens of times in a session adds up. GitSH creates a dedicated Git shell where `git` is implied for every command.

### How GitSH Works

```bash
# Install gitsh
brew install gitsh          # macOS
gem install gitsh           # via RubyGems

# Start the gitsh shell
gitsh

# Inside gitsh — no 'git' prefix needed
@myrepo (main) status       # equivalent to: git status
@myrepo (main) add .        # equivalent to: git add .
@myrepo (main) commit -m "Add login tests"
@myrepo (main) push
@myrepo (main) log --oneline
@myrepo (main) diff main

# Exit gitsh
@myrepo (main) exit
# or press Ctrl+D
```

### GitSH Prompt

The gitsh prompt is context-aware. It shows:

```
@repo-name (branch-name)
```

The branch name updates in real time as you switch branches. This is more informative than a standard bash or zsh prompt.

### GitSH Features

**Tab completion** — GitSH provides completion for Git commands, branch names, remote names, and file paths. Pressing Tab after `checkout` shows all available branches.

**Command history** — press the Up arrow to cycle through previously run Git commands, just like a regular shell.

**Non-git commands still work** — you can run regular shell commands inside gitsh by prefixing them with `!`:

```bash
@myrepo (main) !ls tests/          # run ls
@myrepo (main) !cat .gitignore     # read a file
@myrepo (main) !npx playwright test # run tests
```

**Aliases** — gitsh respects your Git aliases defined in `~/.gitconfig`:

```ini
[alias]
  st = status
  co = checkout
  lg = log --oneline --graph --all
  unstage = restore --staged
```

Inside gitsh these become just `st`, `co`, `lg`, `unstage`.

### GitSH vs. Regular Terminal

| Aspect | Regular Terminal | GitSH |
|---|---|---|
| Command prefix | `git` required before every command | No prefix — implied |
| Branch in prompt | Depends on your shell config | Always shown |
| Tab completion | Depends on plugins (e.g. zsh-completions) | Built in |
| Non-git commands | Run normally | Prefix with `!` |
| Startup time | Instant | Small overhead to start gitsh |
| Best used when | Mixed git and non-git work | Focused git sessions |

### When to Use GitSH

GitSH is most useful when you are doing a focused, extended Git session — resolving conflicts, doing an interactive rebase, reviewing history, or cleaning up a branch before submitting a PR. It is less useful when you are alternating frequently between Git commands and running your tests, because the `!` prefix for non-git commands adds friction.

### Alternatives to GitSH

If gitsh does not suit your workflow, these tools solve similar problems:

| Tool | What it does |
|---|---|
| **Oh My Zsh git plugin** | Adds Git aliases and branch in prompt to zsh |
| **git-aliases** | Adds short aliases like `gst`, `gco`, `gcmsg` |
| **lazygit** | A terminal UI for Git — keyboard-driven, visual |
| **GitLens (VS Code)** | Rich Git integration inside VS Code |
| **GitHub Desktop** | GUI client for GitHub workflows |
| **tig** | Terminal-based Git log browser |

## 10. Common Git Mistakes and How to Fix Them

### Mistake 1 — Committed to the Wrong Branch

You made commits to `main` but they should have been on a feature branch.

```bash
# Create the feature branch at the current position (saves your commits)
git branch feature/login-tests

# Reset main back to where it should be (remote main)
git reset --hard origin/main

# Switch to the feature branch (your commits are there)
git checkout feature/login-tests
```

### Mistake 2 — Committed a Secret or Sensitive File

You accidentally committed a `.env` file or `auth/state.json` containing real tokens.

```bash
# Remove the file from tracking (keeps the file locally)
git rm --cached .env
git rm --cached auth/state.json

# Add to .gitignore immediately
echo ".env" >> .gitignore
echo "auth/" >> .gitignore

# Commit the removal
git commit -m "Remove accidentally committed secrets"
```

> ⚠️ **Critical:** If the commit was already pushed to GitHub, the secret is compromised — it exists in the repository history even after removal. **Immediately rotate the secret** (generate a new token, invalidate the old one). To fully purge it from history, you need `git filter-repo` or contact GitHub support.

### Mistake 3 — Want to Undo the Last Commit (Not Pushed Yet)

```bash
# Undo the commit but keep the changes staged
git reset --soft HEAD~1

# Undo the commit and unstage the changes (changes remain in working directory)
git reset HEAD~1

# Undo the commit AND discard all changes (destructive — cannot be undone)
git reset --hard HEAD~1
```

### Mistake 4 — Want to Undo a Commit That Was Already Pushed

Never use `git reset` on pushed commits — it rewrites history and breaks other people's local copies. Instead, create a new commit that reverses the changes:

```bash
# Create a revert commit (safe — does not rewrite history)
git revert a3f8c2d

# Revert the most recent commit
git revert HEAD
```

### Mistake 5 — Forgot to Add Something to the Last Commit

```bash
# Stage the missing file
git add tests/helpers/auth.ts

# Amend the last commit (adds staged changes to it)
git commit --amend --no-edit   # keep the same commit message
git commit --amend             # open editor to also change the message
```

> ⚠️ Only amend commits that have **not been pushed**. Amending a pushed commit requires a force push which causes problems for others.

### Mistake 6 — Need to Save Work Without Committing (Switching Branches Temporarily)

```bash
# Stash your work-in-progress
git stash

# Switch to another branch, do your work, come back
git checkout main
git pull
git checkout feature/login-tests

# Restore your stashed work
git stash pop

# List all stashes
git stash list

# Apply a specific stash
git stash apply stash@{2}
```

### Mistake 7 — Merge Conflict You Want to Abort

```bash
# Abort a merge in progress and return to the state before merge started
git merge --abort

# Abort a rebase in progress
git rebase --abort
```

### Mistake 8 — Accidentally Deleted a Branch

Git does not immediately destroy commits when you delete a branch — they remain for a while as unreachable objects. You can recover them:

```bash
# Find the commit hash of the deleted branch tip
git reflog

# Recreate the branch from the found hash
git checkout -b feature/recovered-branch a3f8c2d
```

`git reflog` is a log of every position HEAD has been in. It is your safety net for most "I lost my work" situations.

### Mistake 9 — Pushed to the Wrong Remote Branch

```bash
# Force push to overwrite the remote branch (only if you own this branch)
git push origin feature/login-tests --force-with-lease

# --force-with-lease is safer than --force
# It fails if someone else pushed to the remote branch since your last fetch
```

> ⚠️ Never force push to `main` or any shared branch. Force pushing to a shared branch overwrites other people's commits.

## 11. Quick Reference Cheat Sheet

### Setup

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "code --wait"   # VS Code as editor
git config --global init.defaultBranch main
git config --list                                # view all settings
```

### Daily Workflow

```bash
# Start of day — get latest
git checkout main
git pull origin main

# Create branch
git checkout -b feature/my-feature

# Work, then stage and commit
git status
git add .
git status                              # always check before committing
git commit -m "Add descriptive message"

# Push
git push -u origin feature/my-feature

# End of day / ready for PR
git push origin feature/my-feature
# Open PR on GitHub
```

### Branches

```bash
git branch                              # list local branches
git branch -a                          # list all (including remote)
git checkout -b feature/new            # create and switch
git switch feature/existing            # switch (Git 2.23+)
git branch -d feature/merged           # delete merged branch
git branch -D feature/unmerged         # force delete
git push origin --delete feature/old   # delete remote branch
```

### History and Diffs

```bash
git log --oneline
git log --oneline --graph --all
git log --oneline tests/login.spec.ts  # history of one file
git diff                               # working directory changes
git diff --staged                      # staged changes
git diff main feature/my-feature       # between branches
git show a3f8c2d                       # show a specific commit
git blame tests/login.spec.ts          # who wrote each line
```

### Undoing Things

```bash
git restore tests/login.spec.ts        # discard working directory changes
git restore --staged tests/login.spec.ts  # unstage a file
git commit --amend --no-edit           # add to last commit (unpushed only)
git reset --soft HEAD~1                # undo last commit, keep staged
git reset HEAD~1                       # undo last commit, keep in working dir
git revert HEAD                        # safe undo for pushed commits
git stash                              # save work-in-progress temporarily
git stash pop                          # restore stashed work
git reflog                             # history of all HEAD positions (recovery)
```

### Remote

```bash
git remote -v                          # list remotes
git fetch origin                       # download without merging
git pull origin main                   # fetch + merge
git pull --rebase origin main          # fetch + rebase
git push -u origin feature/my-feature # push and set upstream
git push                               # push (after upstream is set)
```

### GitHub CLI (gh)

```bash
# Install: https://cli.github.com
gh auth login
gh pr create --title "Add login tests" --body "..." --base main
gh pr list
gh pr view 42
gh pr merge 42 --squash
gh pr checkout 42         # check out a PR branch locally
gh repo clone org/repo
gh workflow run playwright.yml
```

### Stash

```bash
git stash                              # stash everything
git stash push -m "WIP login tests"   # stash with a name
git stash list                         # see all stashes
git stash pop                          # apply and delete most recent stash
git stash apply stash@{1}             # apply without deleting
git stash drop stash@{1}              # delete a specific stash
git stash clear                        # delete all stashes
```

### Summary — When to Use What

| Situation | Command / Approach |
|---|---|
| Start new work | `git checkout -b feature/name` from up-to-date `main` |
| Save progress regularly | `git add .` + `git commit -m "..."` |
| Sync with remote | `git fetch origin` + `git rebase origin/main` |
| Temporarily set aside work | `git stash` / `git stash pop` |
| Keep feature branch current | `git rebase main` (if not shared) |
| Merge completed feature | PR on GitHub — not direct `git merge` to main |
| Undo unpushed commit | `git reset HEAD~1` |
| Undo pushed commit | `git revert HEAD` |
| Recover lost work | `git reflog` |
| Remove secret from history | `git filter-repo` + rotate the secret |
| Run many git commands in a row | `gitsh` shell |

> 📌 **Final Note:** Git's command surface is large but your daily use is probably just 10 commands — `status`, `add`, `commit`, `push`, `pull`, `checkout`, `branch`, `log`, `diff`, and `stash`. Master those first. Everything else is for handling the situations that arise when things go wrong — and knowing those recovery commands is what separates a confident Git user from someone who re-clones the repository every time something goes unexpected.

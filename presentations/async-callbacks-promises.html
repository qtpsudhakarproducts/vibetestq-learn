What is Synchronous Execution?

One task at a time, in strict order. Each step waits for the previous one to finish completely.

🛒 The Checkout Lane Analogy

Customer 1 finishes → Customer 2 starts → Customer 3 starts. Nobody jumps the queue. Nothing runs in parallel. Completely predictable.

Synchronous Test Steps

  • Open the browser
  • Navigate to login page
  • Type the username
  • Type the password
  • Click the login button
  • Assert dashboard visible

Each step completes before the next begins — exactly what testers need.

What is Asynchronous Execution?

A task can be started and set aside. Other things happen while waiting. Result is handled when ready.

🍽️ The Restaurant Analogy

Waiter takes Table 1's order → doesn't stand at the kitchen waiting → takes Table 2's order → comes back when food is ready. Multiple things happen at once.

Why JavaScript Needs Async

  • Fetching server data — 100ms to 5s
  • Loading a web page — 500ms to 10s
  • Reading a file from disk — 1ms to 100ms
  • Waiting for UI elements — 200ms to 2s
  • Database queries — 5ms to 2s

Without async, JS would freeze the entire browser while waiting — no scrolling, no clicks, nothing.

Why Async Execution Breaks Tests

Test steps MUST run in a specific order. Without handling, JS fires steps before previous ones finish.

❌ Without Async Handling

  • Navigate to login (starts, doesn't wait)
  • Click Login — FIRES TOO EARLY!
  • Fill form — page wasn't ready
  • CRASH — test fails randomly

✅ With Async Handling

  • Navigate → waits for full page load
  • Fill username → waits until done
  • Fill password → waits until done
  • Click Login → waits for confirmation
  • Assert dashboard visible ✓

💡 The whole story of async JS: "How do we make JS wait for slow operations without freezing everything?"

What is a Callback?

A function you hand to another function saying: "When you're done, call this."

📞 The Phone Number Analogy

Like leaving your number at a busy restaurant. Instead of standing at the door waiting, you sit at the bar — and they call you back when your table is ready.

"Don't call us, we'll call you."

Two Types of Callbacks

🔁 Synchronous Callback

Called immediately, in order. Like forEach running your function for each item right now, one at a time.


⏱️ Asynchronous Callback

Called later, when slow work finishes. "Fetch this file — when done, run my function with the result."

Callbacks: Step by Step

Each step passes the next step as a callback argument to the previous step.

1
openBrowser( callback ) — Opens browser; when done, calls next function
CALLS BACK
2
goToLoginPage( callback ) — Navigates; when page loaded, calls next function
CALLS BACK
3
fillCredentials( callback ) — Types credentials; when done, calls next function
CALLS BACK
4
clickLogin( callback ) — Clicks button; when registered, calls next function
CALLS BACK
5
assertDashboardVisible() — Test complete; no more callbacks needed
DONE ✓

⚠️ This works for 5 steps — but what happens with 15, 20, or 30 steps?

The Callback Hell Era

The "Pyramid of Doom" — callbacks nested inside callbacks inside callbacks

openBrowser(function() { goToLoginPage(function() { fillUsername(function() { fillPassword(function() { clickLogin(function() { waitForDashboard(function() { // Finally do something... if you can still read this }) // ← Count these closing brackets. Good luck. }) }) }) }) })

Nobody wanted to write large test suites this way!

Why Callbacks Broke Down

3 Reasons the Pyramid of Doom Was Unworkable

😵 Unreadable Code

Deep nesting impossible to follow. You lose track of which level you're on. Your own test is unreadable a week later.

🐛 Error Nightmare

Must handle errors at every single nesting level. Miss one? Test silently fails with a confusing, misleading message.

🔧 Unmaintainable

Adding a step in the middle requires restructuring the entire pyramid. One change breaks everything that follows it.

A 20-step test = 20 levels of nesting. Debugging meant counting })})}) to find your place. The industry demanded something better.

What is a Promise?

An object representing a value that doesn't exist yet — but will exist in the future. JavaScript says: "I'll get back to you."

📦 The Online Shopping Analogy

You place an order (start the async task). You get an order number (the Promise object). Carry on with your day. The item either arrives ✅ or the order fails ❌. You don't stand at the door waiting.

⏳
Pending
Task in progress. Result not ready yet.
✅
Fulfilled
Task completed successfully. Result is ready.
❌
Rejected
Task failed. An error is available instead.

Once settled (Fulfilled or Rejected), a Promise never goes back to Pending.

How Promises Solved Callback Hell

Instead of nesting, chain steps flat with .then() — each step on its own line, reading top to bottom.

🌐
openBrowser()
→
.then()
navigate
→
.then()
fillForm
→
.then()
clickLogin
→
.then()
assert
→
.catch()
any error

✅ What Promises Fixed

  • No more deep nesting — flat and readable
  • ONE .catch() handles errors from any step
  • Each step clearly on its own line
  • Easy to add, remove, or reorder steps

⚠️ Still Not Perfect

  • Long chains still feel awkward to read
  • Passing data between steps is clunky
  • Doesn't look like normal checklist code
  • Requires "async thinking" to write

The Promise Chaining Problem

With real test suites of 15–30 steps, long .then() chains become a new kind of awkward.

🔗 Sharing Data is Painful

Need a value from Step 2 in Step 6? You must thread it through every step in between — messy and fragile fast.

😕 Doesn't Read Like Steps

Testers think in checklists. A chain of .then() calls still requires async-pattern thinking to read and write.

🐞 Confusing Error Traces

When a chain fails, the stack trace often points to the wrong place. Debugging becomes harder than it should be.

🧩 Conditional Logic is Hard

Branching inside .then() chains based on earlier results turns into spaghetti logic very quickly.

💭 What if async code could look like a plain numbered checklist — but still wait properly?

The Breakthrough: Async / Await (2017)

⏸️ The await Keyword

Put await in front of any async task. JS will pause and wait for that task to finish before moving to the next line. Like pressing pause on a video.

📦 The async Keyword

Mark a function with async to say "this function contains await steps." The container for your sequential steps. Every Playwright test function uses this.

// Result: Clean & Sequential Code ✨ async function runLoginTest() { await openBrowser(); // Wait. Then move on. await goToLoginPage(); // Wait. Then move on. await fillCredentials(); // Wait. Then move on. await clickLogin(); // Wait. Then move on. await assertDashboard(); // ✓ Done! }

📋 Reads exactly like a checklist — top to bottom, one step at a time. This is how testers think.

Error Handling with Async/Await

Uses the same try / catch / finally as normal code — no special async knowledge required.

🎯 try { }

Put your test steps here. The "happy path." JS attempts every step in order until something fails.

🛡️ catch { }

If anything inside try fails, execution jumps here. One place handles all errors for the entire flow.

🔚 finally { }

Runs no matter what — success or failure. Perfect for cleanup: closing browsers, resetting test state.

try = follow the steps  ·  catch = handle failure  ·  finally = always clean up

Same pattern works in every programming language — now working naturally with async operations.

Why Playwright is Fully Async

Playwright talks to a real browser over a connection. Every single action returns a Promise.

🖱️ page.click()

Returns a Promise. Browser must process the click and confirm it happened before the test moves on.

⌨️ page.fill()

Returns a Promise. Browser must locate the field, focus it, and finish entering every character.

🌍 page.goto()

Returns a Promise. Browser must download, parse, and fully render the page before returning.

Without await, your test fires all commands at once — click, fill, and navigate simultaneously. await enforces your exact step order.

What Happens If You Forget await?

The most common mistake — doesn't always cause an obvious crash, which makes it more dangerous.

❌ Missing await

  • page.goto("/login") — starts, doesn't wait
  • page.fill("#username") — fires immediately
  • ERROR: Element not found!
  • Page hadn't finished loading yet
  • Test fails randomly — hard to reproduce

✅ Properly awaited

  • await page.goto("/login") — page loads ✓
  • await page.fill("#username") — field ready ✓
  • await page.fill("#password") — filled ✓
  • await page.click("#submit") — clicked ✓
  • Test passes reliably every time ✓

🚦 Think of await as a red traffic light. Without it, you're running every red light — a crash is inevitable.

Playwright Error Messages vs Promise Rejections

Playwright throws specific, readable error messages — not raw promise rejection errors. This makes debugging much easier.

❌ Generic Promise Rejection

  • UnhandledPromiseRejectionWarning
  • Promise rejected with undefined
  • No useful detail about what went wrong
  • Hard to map to a specific test step

✅ Playwright Specific Errors

  • "Locator not found" — element missing
  • "Timeout exceeded" — element too slow
  • "Strict mode violation" — multiple matches
  • "Navigation failed" — page didn't load

⚠️ Even though Playwright handles some exceptions automatically, you still need try-catch to customise error messages and prevent runtime crashes in your test framework.

Useful Promise Methods

Beyond basic promises — methods for running multiple async operations together.

⚡ Promise.all()

Runs multiple Promises in parallel. Waits for ALL to finish. If even one fails, the whole thing fails. Use when all results are required.

e.g. Run 3 API calls at once, wait for all responses.

🛡️ Promise.allSettled()

Runs multiple Promises in parallel. Waits for ALL to finish — success or failure. Never rejects. Gives you each result individually.

e.g. Check 5 elements — report pass/fail for each.

🏁 Promise.race()

Runs multiple Promises. Returns as soon as the first one settles — win or fail. Used in Playwright internally for timeout races.

e.g. Race a page load against a 5s timeout.

🎯 Promise.any()

Returns as soon as the first one succeeds. Ignores failures. Only fails if ALL promises reject.

e.g. Try 3 locators — use whichever is found first.

Playwright Auto-Waiting

Playwright goes beyond Promises — most actions automatically check the element is ready before acting.

🔍 Auto-checks before acting

Before clicking or filling, Playwright checks: Is the element visible? Is it enabled? Is it stable (not animating)? Only then does it act.

No manual sleep() calls needed!

⏱️ Explicit waitFor Methods

  • waitForSelector('.element') — element appears
  • waitForURL('**/dashboard') — URL matches
  • waitForResponse('**/api') — network call done
  • waitForLoadState('networkidle') — all quiet

Playwright's auto-waiting means your tests are more reliable out of the box — without extra wait boilerplate.

How to Explain This in an Interview

These concepts are asked in almost every Playwright / JS automation interview. Here's how to answer clearly.

Q: What is a callback in JavaScript?
A function passed to another function as an argument, to be called once the async task completes. Used to handle the result of operations like reading files or fetching data. Main problem: deeply nested callbacks become Callback Hell.
Q: What is a Promise and what are its states?
A Promise represents a future value. It has 3 states: Pending (in progress), Fulfilled (succeeded), and Rejected (failed). Once settled, it never changes state again.
Q: What is async/await and why was it introduced?
Syntactic sugar over Promises that lets you write async code in a linear, synchronous-like manner. Introduced to fix Promise chaining complexity — use await before any Promise-returning call; handle errors with a catch block.
Q: Why does every Playwright method use async/await?
Every Playwright action (click, fill, goto) sends a command to a real browser and waits for a response — all are async operations that return Promises. Without await, steps fire simultaneously in unpredictable order.

⏱️ Everything Takes Time

Browser actions are slow. async/await handles that without freezing or losing step order.

📋 await = Pause & Wait

Every Playwright action needs await. It's the pause button that keeps your steps in the right order.

🤝 Promises Power It All

Under the hood, every async operation is a Promise. await just makes them readable and linear.

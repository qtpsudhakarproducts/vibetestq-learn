What is a Locator?

A locator is an instruction that tells your test framework exactly which element on the page to interact with.

🗺️ The Postal Address Analogy

Just as "42 Main Street, Floor 3, Room B" uniquely identifies a room in a building — a locator uniquely identifies one element on a web page.

Without a precise address, the postman (your test) delivers to the wrong door — or gets lost entirely.

🎯 Why Locators Matter

  • Every test action needs a target element
  • Bad locators = flaky, broken tests
  • Good locators = stable, maintainable tests
  • They reflect how users experience the page

HTML Anatomy — What Locators Target

Every attribute on an HTML element is a potential locator handle.

<button id="login-btn" class="btn btn-primary" type="submit" data-testid="login-button" aria-label="Log in to account" >Log In</button> <label for="username">Username</label> <input id="username" type="text" placeholder="Enter username" name="username" >

Key Attributes for Locators

  • id — Unique identifier. Best for CSS & XPath.
  • class — Style classes. Common but fragile.
  • type — Input type (text, submit, checkbox…)
  • name — Form field name attribute.
  • placeholder — Hint text in input fields.
  • data-testid — Custom test attribute (best!)
  • aria-label — Accessibility label.
  • href, src, alt — Link and image attributes.

💡 Always look for id first — it must be unique per page.

Playwright Inspection Tools — Overview

Playwright has built-in tools that generate locators for you — no manual inspection needed.

🎭 Codegen

npx playwright codegen https://example.com

Records interactions and generates test code. Best for exploring new pages.

🖥️ UI Mode

npx playwright test --ui

Interactive test runner with time-travel debugging. Best for debugging failing tests.

🐛 Debug Mode

npx playwright test login.spec.ts --debug

Step through code line by line. Best for step-by-step investigation.

⏸️ page.pause()

await page.pause(); // Pauses here

Pause at a specific point in your test. Best for mid-test inspection.

Codegen & UI Mode — Workflows

⚡ Codegen Workflow

  • Run npx playwright codegen <url>
  • Browser opens automatically
  • Click Pick Locator 🎯 button
  • Hover & click any element on the page
  • Playwright suggests the best locator
  • Copy locator directly into your test code

✨ Perfect for exploring new pages and getting locators quickly!

🔍 UI Mode — Explore Panel

// Type in Explore panel page.getByRole('button') // Shows: "3 found" // Refine it page.getByRole('button', { name: 'Login' }) // Shows: "1 found" ✅
  • Type locators → see results in real-time
  • Time-travel: click any step to see page state
  • Pick Locator 🎯 available in every step

✨ Best for verifying locators work before using them!

Debug Mode & page.pause() — When to Use Which

🐛 Debug Mode

  • Test pauses at the very first line
  • Step through code with F10
  • Browser updates in real-time at each step
  • Pick Locator 🎯 available throughout

⏸️ page.pause()

  • Pauses at exactly where you place it
  • No need to step through the whole test
  • Explore Panel and Pick Locator available
  • Remove after debugging!

Which tool to use?

  • 1 Exploring new page? → npx playwright codegen <url>
  • 2 Writing new test? → VSCode Extension (Pick Locator button)
  • 3 Test failing? → npx playwright test --ui
  • 4 Need step-by-step? → npx playwright test --debug
  • 5 Pause at one spot? → await page.pause()

Chapter 3

CSS Selectors

ID · Class · Attributes · Combinators · Pseudo-classes

CSS Selectors — The Foundation

CSS Selectors were designed to style pages — they're equally powerful for locating elements in tests.

By ID  FASTEST

#login-btn #username #submit-form

Use # prefix. Must be unique on the page.

By Class  CAREFUL

.btn-primary .btn.btn-primary [class*="btn-"]

Use . prefix. Classes can match many elements.

By Tag  AVOID ALONE

button input a

Tag name alone is too broad. Always combine with other selectors.

✅ Best: Use id or specific data-testid attributes — these don't change with styling.

❌ Avoid: Chaining many classes like .col-md-6.active.disabled.btn — any style change breaks the test.

CSS — Attribute Selectors

The most powerful CSS selectors for test automation — target any attribute, not just id and class.

/* Exact attribute value */ [type="submit"] [name="username"] [data-testid="login-btn"] /* Attribute exists (any value) */ [disabled] [readonly] /* Contains substring */ [class*="btn"] [href*="login"] /* Starts with */ [id^="user"] /* Ends with */ [id$="-btn"] /* Element + attribute combined */ input[type="text"] button[type="submit"]

data-testid Pattern (Recommended)

<!-- Ask devs to add --> <button data-testid="submit-btn"> Submit </button> // In test [data-testid="submit-btn"]

💡 data-testid is immune to styling changes — developers add it purely for testing purposes.

CSS — Combinators & Pseudo-Classes

Combinators

/* Descendant — any depth */ form input /* Direct child only */ form > input /* Adjacent sibling — next only */ label + input /* General sibling — all after */ label ~ input

Pseudo-Classes

/* Position */ li:first-child li:last-child li:nth-child(2) /* State */ input:disabled input:checked button:not([disabled])

Real-World Examples

/* Username field inside login form */ #login-form input[name="username"] /* Submit button in a form */ form button[type="submit"] /* Second row in a table */ table tr:nth-child(2) /* Error message after input */ input + .error-message /* Active navigation link */ nav a.active /* Enabled submit button only */ button[type="submit"]:not([disabled]) /* Checked checkbox */ input[type="checkbox"]:checked

Chapter 4

XPath

Relative XPath · Predicates · Functions · Axes

XPath — Absolute vs Relative

XPath navigates the HTML like a file system — using paths from a starting point to a target element.

❌ Absolute XPath — Never Use

/html/body/div[1]/div[2]/form/input[1]
  • Starts from /html root
  • Any DOM change = broken test
  • Browser "Copy XPath" generates this!
  • Never use in real tests

✅ Relative XPath — Always Use

//input[@id="username"] //button[text()="Login"] //input[@placeholder="Enter email"]
  • Starts with // — searches anywhere in DOM
  • Targets elements by their attributes
  • Resilient to page restructuring
  • Always use relative XPath

XPath Syntax: //tagName[@attribute='value'] — double slash = search anywhere, square brackets = conditions.

XPath — Predicates & Text Functions

# Exact attribute match //input[@id='username'] //button[@type='submit'] # Multiple conditions (AND) //input[@type='text' and @name='email'] # Either condition (OR) //button[@type='submit' or @type='button'] # Attribute exists //input[@disabled] # Position index (//input)[1] (//tr)[2]
# Exact text match //button[text()='Login'] # Contains text (partial match) //button[contains(text(),'Log')] # Contains attribute value //div[contains(@class,'active')] # Starts-with //input[starts-with(@id,'user')] # Normalize whitespace //button[normalize-space()='Sign In']

💡 contains() is your best friend — partial matches survive label changes and extra whitespace.

XPath Axes — Navigate Relationships

Axes let you navigate up, down, and sideways — the unique superpower of XPath over CSS.

# parent:: — move UP one level //input[@id='email']/parent::div # ancestor:: — move UP any level //input/ancestor::form # following-sibling:: — next sibling //label[text()='Email'] /following-sibling::input # preceding-sibling:: — prior sibling //input/preceding-sibling::label # descendant:: — all nested children //div[@id='menu']/descendant::a

🌟 The Most Powerful Pattern

# Find input by its label text //label[text()='Email'] /following-sibling::input # Find error after a field //input[@name='email'] /following-sibling::span[@class='error'] # Checkout button in cart section //section[@id='cart'] //button[text()='Checkout']

💡 Axes solve the problem of elements with no unique attributes — navigate from something you can find to what you need.

CSS vs XPath — When to Use Each

CapabilityCSS SelectorXPath
Find by ID✅ #id (very fast)✅ //*[@id="..."]
Find by class✅ .classname✅ @class contains
Find by exact text❌ Not supported✅ [text()='Login']
Find by partial text❌ Not supported✅ contains(text(),'Log')
Navigate to parent❌ Not supported✅ /parent::div
Navigate siblings⚠️ Only next (+)✅ following-sibling
Attribute contains✅ [attr*="val"]✅ contains(@attr,'val')
Readability✅ Simpler syntax⚠️ More verbose
Performance✅ Faster⚠️ Slightly slower

Use CSS for simple id/class/attribute selections. Use XPath when you need to navigate relationships or match by text content.

Chapter 5

Playwright Locators

7 Strategies · Chaining · Filtering · Best Practices

Playwright — A Different Philosophy

Playwright doesn't ask "where is this element in the DOM?" — it asks "how does a user see and interact with this element?"

❌ Old Way — DOM View

// Brittle, developer-centric page.click('#submit-btn-123'); page.click('//div[@class="row"]/button[2]'); // Breaks when DOM changes

✅ Playwright Way — User View

// Resilient, user-centric page.getByRole('button', { name: 'Submit' }) page.getByLabel('Email address') // Survives DOM restructuring

Auto-Waiting

Waits for element to be ready before acting. No explicit waits needed.

Auto-Retry

Retries finding the element until action succeeds or timeout.

Strict Mode

Fails if locator matches more than one element. Forces precision.

7 Built-in Playwright Locator Strategies

getByRole()

ARIA roles — Most resilient

getByLabel()

Form labels — Best for inputs

getByText()

Visible text content

getByPlaceholder()

Input placeholder hints

getByTestId()

data-testid attributes

getByAltText()

Image alt text

getByTitle()

Title tooltip attributes

7 semantic strategies + page.locator() for CSS/XPath fallback = complete coverage for any element.

1 getByRole() & 2 getByLabel()

getByRole() — Most Resilient

// Simple role page.getByRole('button') // Role + accessible name page.getByRole('button', { name: 'Login' }) // Regex name match page.getByRole('link', { name: /sign.?up/i }) // Heading level page.getByRole('heading', { level: 1 }) // Checked checkboxes page.getByRole('checkbox', { checked: true })

Common roles: button, link, textbox, checkbox, radio, combobox, heading, dialog, navigation, table, row, cell

getByLabel() — Best for Forms

// Exact label match page.getByLabel('Username').fill('admin') // Case-insensitive regex page.getByLabel(/email/i).fill('test@test.com') // Checkbox via label page.getByLabel('Remember me').check() // Works with for/id, wrapping labels, // and aria-labelledby — all 3 patterns!

✅ getByRole + getByLabel cover 90% of all test automation needs.

3 getByText() & 4 getByPlaceholder()

getByText() — Visible Text Content

// Exact match (default) page.getByText('Welcome Back') // Partial / substring page.getByText('Welcome', { exact: false }) // Regex — case insensitive page.getByText(/welcome back/i) // Wait for message to appear page.getByText('Login successful').waitFor()

Best for: verifying messages, headings, status text, notifications.

getByPlaceholder() — Input Hints

<!-- HTML --> <input placeholder="Enter your email"> <input placeholder="Search products..."> // Test code page.getByPlaceholder('Enter your email') .fill('test@example.com') page.getByPlaceholder('Search', { exact: false }) .fill('playwright') page.getByPlaceholder(/message/i) .fill('Hello there')

Best for: inputs without a visible label. Use when getByLabel() has nothing to match.

5 getByTestId()   6 getByAltText()   7 getByTitle()

getByTestId()

<!-- Add to HTML --> <button data-testid="submit-btn" >Submit</button> // Use in test page.getByTestId('submit-btn') .click()

✅ Ask devs to add data-testid. Immune to any style changes.

getByAltText()

<!-- Image with alt --> <img src="logo.png" alt="Company Logo" > // Use in test page.getByAltText('Company Logo') .isVisible() page.getByAltText(/logo/i).click()

✅ Best for images, icons, avatars. Also validates accessibility.

getByTitle()

<!-- Element with title --> <button title="Close dialog" >✕</button> // Use in test page.getByTitle('Close dialog') .click() page.getByTitle(/close|dismiss/i) .click()

✅ Best for icon buttons (✕, ?, ℹ) with no visible text.

Chaining Locators — Precision Through Context

Search within a parent locator instead of the whole page — prevents strict mode errors from duplicate elements.

// Button inside a product card page.locator('.product-card') .getByRole('button', { name: 'Add to Cart' }) .click() // Link inside navigation only page.getByRole('navigation') .getByRole('link', { name: 'Products' }) .click() // OK button inside confirm dialog page.getByRole('dialog', { name: 'Confirm' }) .getByRole('button', { name: 'OK' }) .click()
// Specific cell in a table row const cell = page .getByRole('table') .getByRole('row', { name: /John Smith/i }) .getByRole('cell') .nth(2) // Email field inside a modal page.getByRole('dialog') .getByLabel('Email') .fill('test@example.com') // iFrame locator page.frameLocator('#payment-iframe') .getByLabel('Card Number') .fill('4111111111111111')

Chaining = Precision + Context + Readability

Filtering Locators — Narrow Multiple Matches

Use .filter() to pick the right element from multiple matches without rewriting the base locator.

// Filter by text — exact page.getByRole('listitem') .filter({ hasText: 'Active' }) .click() // Filter by text — regex page.getByRole('listitem') .filter({ hasText: /active/i }) // Chain multiple filters (AND) page.getByRole('listitem') .filter({ hasText: 'Active' }) .filter({ hasText: 'Priority' }) // Count matching elements await page.getByRole('listitem') .filter({ hasText: 'Done' }) .count()
// Filter by child element page.getByRole('row') .filter({ has: page.getByRole('checkbox') }) // Card that has an "Edit" button page.locator('.card') .filter({ has: page.getByRole('button', { name: 'Edit' }) }) .getByRole('button', { name: 'Delete' }) .click() // Iterate all matching items const items = page.getByRole('listitem') for (const item of await items.all()) { await item.textContent() }

filter({hasText}) and filter({has: locator}) — combine them for surgical precision.

Real-World Example — Login Test

import { test, expect } from '@playwright/test'; test('user can log in', async ({ page }) => { await page.goto('https://example.com/login'); // ✅ getByLabel for form fields await page.getByLabel('Username') .fill('admin'); await page.getByLabel('Password') .fill('secret123'); // ✅ getByRole for checkbox await page .getByRole('checkbox', { name: 'Remember me' }) .check(); // ✅ getByRole for button await page .getByRole('button', { name: 'Log In' }) .click(); // ✅ Assert via getByRole await expect( page.getByRole('heading', { name: 'Dashboard' }) ).toBeVisible(); });

What Makes This Great?

  • getByLabel for all inputs — resilient
  • getByRole for buttons — semantic
  • No CSS selectors or XPath needed
  • Auto-waits at every step
  • Reads like plain English
  • No explicit waits or sleeps

Common Assertions

expect(locator).toBeVisible() expect(locator).toBeHidden() expect(locator).toHaveText('...') expect(locator).toBeEnabled() expect(locator).toBeChecked() expect(locator).toHaveCount(3)

Best Practices — Do This, Avoid That

Do This

  • Use getByRole, getByLabel first
  • Make locators descriptive and readable
  • Leverage auto-waiting — no explicit waits
  • Chain locators to narrow down context
  • Use filter() to pick from multiple matches
  • Ask devs to add data-testid where needed
  • Use relative XPath when XPath is needed
  • Test your locator in browser console first

Avoid

  • Absolute XPath starting with /html
  • Long CSS class chains (.a.b.c.d)
  • Position-only selectors (.nth(3)) without context
  • ElementHandle page.$() API (legacy)
  • Hard-coded sleeps / arbitrary delays
  • Relying on auto-generated IDs (#btn-1234)
  • Browser "Copy XPath" without reviewing
  • Testing implementation details

Write tests from a user's perspective, not a developer's. If a user can see and interact with it — your locator should reflect that.

Key Takeaways

🔍 Inspect Before Writing

Use DevTools to understand element structure, attributes, and accessibility roles. Test in console before using in code.

🎭 Use Playwright Tools

Codegen, UI Mode, Debug Mode, and page.pause() generate locators for you — choose the right tool for the job.

🎯 CSS = Simple, XPath = Navigational

CSS for id/class/attribute. XPath when you need to match text or traverse parent/sibling relationships.

🌟 Playwright Semantic First

getByRole → getByLabel → getByPlaceholder → getByText → getByTestId → CSS/XPath as last resort.

⚡ Auto-Wait = No Sleeps

Playwright auto-waits before every action. Never use setTimeout. Use waitFor() only for custom conditions.

🏗️ Think Like a User

Semantic locators validate accessibility too. If a user can see and interact with it, your locator should reflect that.

# WF1 — Requirements → Test Scenarios

> The gateway workflow. Without this, everything downstream produces hollow output.

---

## 1. What it is

Given a user story or requirement, AI extracts testable conditions, flags ambiguity, drafts scenarios, and stores them linked to the REQ-ID — before developers write any code.

A human would take hours. This runs in minutes.

---

## 2. Who owns it

**QA leads own the process.** QA engineers run it on every new requirement.

BAs and POs are involved as *reviewers* when AI flags ambiguity — but they don't drive the workflow.

---

## 3. Tools needed

From the 7 categories:
- **Category 2 — MCPs:** Playwright MCP (to validate testability against current code)
- **Category 3 — AI IDE:** Cursor / Copilot / Antigravity (drives the workflow)
- **Category 4 — Platform AI:** Rovo or a Jira MCP (reads the Jira story, writes the scenarios back)

---

## 4. Step-by-step setup

### Step 1: Ensure the requirement exists in your repo

If requirements live in Jira, create a script or hook that syncs the story to `requirements/REQ-142.md` when it moves to "Ready for QA."

Rovo can do this on Atlassian. A custom MCP agent can do this for other platforms.

### Step 2: Create the scenario template

Save as `.ai/templates/scenario-template.md`:

```markdown
# Scenarios for REQ-{id}: {title}

**Linked requirement:** requirements/REQ-{id}.md
**Last generated:** {timestamp}
**Generated by:** ai-agent
**Approved by:** (pending)

## Testability review

**Ambiguities detected:**
- (AI lists here)

**Questions for BA:**
- (AI lists here)

## Scenarios

### Scenario 1: Happy path
**Given** ...
**When** ...
**Then** ...

### Scenario 2: Edge case
...

### Scenario 3: Error state
...
```

### Step 3: Create the prompt

Save as `.ai/prompts/wf1-generate-scenarios.md`:

```markdown
# Task: Generate test scenarios from a requirement

## Context files to read (in order)
1. .ai/project-context.md — what this product does
2. .ai/conventions.md — our scenario conventions
3. requirements/REQ-{id}.md — the requirement to process
4. .ai/graph.json — to see existing linked scenarios (if any)

## Your job
1. **Read the requirement fully.** Identify every testable condition.
2. **Detect ambiguity.** List anything vague, missing, or contradictory.
3. **Generate scenarios.** Use Given/When/Then. Cover:
   - Happy path (1–2)
   - Edge cases (boundary values, empty inputs, max inputs)
   - Error states (invalid input, network failure, auth failure)
   - Non-functional (performance if relevant, security, a11y if relevant)
4. **Link back to REQ-ID** in every scenario comment.

## Rules
- Never invent acceptance criteria not in the requirement.
- If ambiguity exists, LIST IT. Don't guess.
- Scenarios must be executable by a tester — not abstract.
- Use the template in .ai/templates/scenario-template.md

## Output
Write to: scenarios/REQ-{id}-scenarios.md
Append an entry to graph.json under the REQ-ID.
```

### Step 4: Run it

In your AI IDE, invoke the prompt:

```
@prompt wf1-generate-scenarios.md for REQ-142
```

Or, via MCP command from a script.

### Step 5: Review

A human QA reads the output. Specifically:
- Are the ambiguities real? If yes, send back to BA.
- Are the scenarios aligned with what the PM actually wants?
- Any missing cases the AI didn't see?

Mark the file as approved:

```markdown
**Approved by:** @sudhakar
**Approved date:** 2026-04-17
```

### Step 6: Update graph.json

The AI should do this automatically in Step 4. Verify:

```json
{
  "id": "REQ-142",
  "scenarios_file": "scenarios/REQ-142-scenarios.md",
  "scenarios_approved": true,
  "scenarios_approved_by": "sudhakar"
}
```

## 5. Prompts & templates

### Minimal prompt (if you just want to try)

```
Read requirements/REQ-142.md.

Generate test scenarios covering:
- happy path
- 2-3 edge cases
- error states

Use Given/When/Then format. List any ambiguities you find.
Output to scenarios/REQ-142-scenarios.md.
```

### Better prompt (for production)

Use the prompt in Step 3 above. It references project context, conventions, and graph.json.

### Ambiguity detection prompt

When you only want to check if a requirement is testable (without generating scenarios yet):

```
Read requirements/REQ-142.md.

Do NOT generate scenarios yet.

Tell me:
1. Is this requirement fully testable? (Yes/No)
2. What ambiguities would block a tester?
3. What clarifying questions would you ask the BA?

If your answer to Q1 is No, STOP. The requirement needs refinement first.
```

This is useful as a **pre-development gate** — use in Type 2 (Spec-Driven) SDLC.

---

## 6. Success criteria

- [ ] Every REQ-ID in active development has a `scenarios/REQ-X-scenarios.md` file
- [ ] Every scenarios file is approved by a human before dev starts
- [ ] Time from "requirement received" to "approved scenarios" is measured in hours, not days
- [ ] Ambiguities are flagged *before* development — not discovered in UAT
- [ ] `graph.json` shows the scenario linkage for every REQ

---

## 7. Common pitfalls

### 🚫 Accepting scenarios without human review
The whole point is **QA shapes quality before dev starts.** If you rubber-stamp AI output, you lose the gate.

### 🚫 Vague requirements → vague scenarios
Garbage in, garbage out. If the BA writes "user should be able to log in," AI will generate plausible but hollow scenarios. Require requirements to have measurable acceptance criteria before this workflow runs.

### 🚫 No linkage in graph.json
If you generate scenarios but don't update `graph.json`, downstream workflows (WF8, WF11) won't find them. Enforce the linkage in the prompt.

### 🚫 Skipping ambiguity detection
The ambiguity report is often more valuable than the scenarios themselves. Don't skip it to save time.

### 🚫 One-shot generation
Treating scenarios as "generated once, used forever." Requirements evolve. Re-run WF1 when the requirement changes.

## 8. Which SDLC type it fits

| Type | Fit | How it looks |
|------|-----|--------------|
| 1 — AI-Assisted | Manual | QA runs WF1 in their IDE on their own initiative |
| 2 — Spec-Driven | **Core gate** | No dev starts until WF1 scenarios are approved |
| 3 — Parallel Stream | **Core gate** | WF1 runs the moment a spec is ready; Dev + QA work off the approved scenarios |
| 4 — Agentic | Automated | An agent triggers WF1 when a requirement is created, notifies QA when ready |
| 5 — Regulated | **Core + audit** | Same as 4, plus the approval is logged with timestamp/reviewer for audit |

## 9. What to try next

Once WF1 is running on every new requirement:

- **WF5 (Automation Generation)** — next logical step. AI generates Playwright tests from the approved scenarios.
- **WF8 (Coverage Audit)** — start measuring whether your existing test suite covers the scenarios.
- **WF3 (Test Data Design)** — if scenarios reference complex data, run WF3 to generate the data automatically.

## Example — end to end

**Input:** `requirements/REQ-142.md`
```markdown
# REQ-142: Password reset via email

## User story
As a registered user, I want to reset my password via email so I can recover access.

## Acceptance criteria
- User requests reset on login page
- Email sent within 60 seconds
- Reset link valid for 30 minutes
- Rate limit: 5 requests per user per hour
```

**Output:** `scenarios/REQ-142-scenarios.md`
```markdown
# Scenarios for REQ-142: Password reset via email

**Linked requirement:** requirements/REQ-142.md
**Last generated:** 2026-04-17T14:22:00Z
**Generated by:** ai-agent

## Testability review

**Ambiguities detected:**
- What counts as a "registered user"? (verified email? SSO-linked?)
- Does "rate limit: 5 per user per hour" apply per IP, per account, or both?
- If an email is already valid and in-flight, does a new request invalidate it?

**Questions for BA:**
1. Should SSO users see the reset option at all?
2. What's the exact copy for the email?
3. What happens on the 6th request in an hour?

## Scenarios

### Scenario 1: Happy path
**Given** a registered user with a valid email
**When** they request a password reset
**Then** an email is sent within 60 seconds
**And** the reset link is valid for 30 minutes

### Scenario 2: Rate limit boundary
**Given** a user has made 4 reset requests in the last hour
**When** they make a 5th request
**Then** the request succeeds

### Scenario 3: Rate limit exceeded
**Given** a user has made 5 reset requests in the last hour
**When** they make a 6th request
**Then** the request is rejected with a 429 status
**And** an error message is shown: "Too many reset requests, try again in X minutes"

### Scenario 4: Expired link
**Given** a valid reset link has been issued
**When** 31 minutes pass
**And** the user clicks the link
**Then** the user sees "Link expired, please request a new one"

### Scenario 5: Email delivery failure
**Given** the email service is unavailable
**When** a user requests a reset
**Then** the UI shows "Something went wrong, please try again"
**And** the failure is logged for ops
```

Notice: the ambiguity section caught three real questions the AC didn't answer. That's the unlock.

# 18 — CI Integration

## The Scenario

Your test suite works perfectly locally. But three things keep happening on the team:

Someone pushes code without running tests. The suite breaks. Nobody knows until the next morning.

Tests pass locally on macOS but fail on the Linux CI server. Different Node.js version, different font rendering, different path separators.

A CI run fails but the report is gone. The terminal logs have scrolled off and no artefacts were uploaded. You have a pass/fail count but no screenshots, no traces, no detail.

CI integration solves all three. Tests run automatically on every push in a consistent environment, and artefacts are always available.

---

## What CI Integration Means for Playwright

A properly integrated Playwright suite:

- Runs automatically on every push and pull request — no human needs to remember
- Runs in a reproducible environment — same Node version, same OS, same browser versions every time
- Uploads the HTML report and traces even when tests fail — the report is available precisely when you need it
- Blocks merges when tests fail — broken code cannot reach main
- Provides feedback in minutes — engineers know quickly whether their change broke something

## GitHub Actions — Complete Setup

```yaml
# .github/workflows/playwright.yml
name: Playwright Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]
  schedule:
    - cron: '0 2 * * *'     # nightly at 2am UTC

jobs:
  test:
    name: Playwright Tests
    runs-on: ubuntu-latest
    timeout-minutes: 60

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run tests
        run: npx playwright test
        env:
          CI: true
          BASE_URL: ${{ secrets.BASE_URL }}

      - name: Upload HTML report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30

      - name: Upload test results
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-results
          path: test-results/
          retention-days: 7
```

**`npm ci` not `npm install`** — installs exactly the versions in `package-lock.json`. No unexpected upgrades between runs.

**`npx playwright install --with-deps`** — installs browsers and their OS-level dependencies (fonts, shared libraries). On a fresh Ubuntu runner these are not pre-installed. Without `--with-deps` the browser launch fails.

**`if: always()`** on upload steps — uploads the report even when the test step fails. Without this, the upload step is skipped on failure — meaning you have no report exactly when you need one.

**`CI: true`** — your `playwright.config.ts` reads this to enable retries, adjust workers, and configure the right reporters.

## Caching Browsers

Installing browsers takes 1–3 minutes on every run. Cache them so installation is skipped when nothing has changed:

```yaml
- name: Cache Playwright browsers
  uses: actions/cache@v4
  id: playwright-cache
  with:
    path: ~/.cache/ms-playwright
    key: playwright-${{ hashFiles('package-lock.json') }}

- name: Install Playwright browsers
  if: steps.playwright-cache.outputs.cache-hit != 'true'
  run: npx playwright install --with-deps

- name: Install OS deps only (cache hit)
  if: steps.playwright-cache.outputs.cache-hit == 'true'
  run: npx playwright install-deps
```

When `package-lock.json` has not changed the cache is used and browser installation is skipped. OS dependencies are reinstalled on every run because they are not cached — they come from the system package manager and are not in `~/.cache/ms-playwright`.

## CI-Aware Configuration

Your `playwright.config.ts` should behave differently in CI. The `CI` environment variable (set automatically by GitHub Actions, GitLab CI, Azure DevOps, CircleCI, and most other platforms) is the standard way to detect the environment:

```typescript
// playwright.config.ts
export default defineConfig({
  // Retries absorb environmental flakiness on CI
  retries: process.env.CI ? 2 : 0,

  // Fewer workers on CI — shared runner, not a dedicated dev machine
  workers: process.env.CI ? 2 : 4,

  // Prevent accidental test.only from blocking the entire CI run
  forbidOnly: !!process.env.CI,

  // Stop after 10 failures — no point running 500 more tests
  maxFailures: process.env.CI ? 10 : undefined,

  use: {
    // Always capture evidence on CI
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    trace: 'on-first-retry',
  },

  reporter: process.env.CI
    ? [
        ['html', { open: 'never' }],
        ['junit', { outputFile: 'results/junit.xml' }],
        process.env.GITHUB_ACTIONS ? ['github'] : ['dot'],
      ]
    : [
        ['html', { open: 'on-failure' }],
        ['list'],
      ],
});
```

`forbidOnly` — if a developer accidentally commits `test.only`, every other test is skipped and CI passes on one test. `forbidOnly: true` makes `test.only` a CI error instead.

`maxFailures` — if 10 tests fail, something is clearly broken. Stop the run rather than spending 20 more minutes on tests that will also fail.

## Secrets and Environment Variables

Never hardcode credentials or environment URLs in test files. Pass them through CI secrets:

```typescript
// playwright.config.ts — reads from environment
export default defineConfig({
  use: {
    baseURL: process.env.BASE_URL ?? 'https://demo.orangehrmlive.com',
  },
});
```

```yaml
# GitHub Actions — secrets injected from repository settings
- name: Run tests
  run: npx playwright test
  env:
    CI: true
    BASE_URL: ${{ secrets.STAGING_URL }}
    TEST_USERNAME: ${{ secrets.TEST_USERNAME }}
    TEST_PASSWORD: ${{ secrets.TEST_PASSWORD }}
```

Secrets are encrypted in GitHub and never appear in logs. Configure them in Settings → Secrets and variables → Actions.

## JUnit XML — CI Platform Test Reporting

Most CI platforms can parse JUnit XML and display test results natively — showing pass/fail trends, individual test details, and failure history without opening a separate report.

```typescript
reporter: [
  ['html', { open: 'never' }],
  ['junit', { outputFile: 'results/junit.xml' }],
],
```

**Azure DevOps:**

```yaml
- task: PublishTestResults@2
  condition: always()
  inputs:
    testResultsFormat: 'JUnit'
    testResultsFiles: 'results/junit.xml'
    testRunTitle: 'Playwright Tests'
    failTaskOnFailedTests: true
```

**GitLab CI:**

```yaml
artifacts:
  reports:
    junit: results/junit.xml
  paths:
    - playwright-report/
  when: always
  expire_in: 30 days
```

## GitHub Actions — Inline PR Annotations

The `github` reporter formats failures as annotations that appear directly on the pull request diff. Reviewers see failing tests without opening workflow logs.

```typescript
reporter: [
  ['html', { open: 'never' }],
  process.env.GITHUB_ACTIONS ? ['github'] : ['dot'],
],
```

`process.env.GITHUB_ACTIONS` is set automatically by GitHub Actions. This ensures the github reporter only activates there — on other CI platforms it falls back to dot.

## The .gitignore

These are generated on every run and must not be committed:

```
# .gitignore
test-results/
playwright-report/
blob-report/
.auth/
results/
```

Snapshot files (`snapshots/`) should be committed — they are visual test baselines.

## Key Points

- CI runs tests automatically on every push — removing the need for anyone to remember
- `npm ci` — reproducible installs from the lock file; use instead of `npm install`
- `npx playwright install --with-deps` — required on fresh CI runners; installs browsers and OS dependencies
- `if: always()` on artefact uploads — uploads report even when tests fail; critical
- `CI=true` — detected by config to enable retries, adjust workers, configure reporters, enforce `forbidOnly`
- Cache `~/.cache/ms-playwright` keyed on `package-lock.json` hash — skips browser reinstallation
- `forbidOnly: !!process.env.CI` — turns accidental `test.only` commits into a CI error
- `maxFailures` — stops the run early when something is clearly broken
- JUnit XML — standard format consumed by Azure DevOps, GitLab, Jenkins, CircleCI for native test reporting
- GitHub reporter — produces inline PR annotations; use only when `process.env.GITHUB_ACTIONS` is set
- Secrets via CI secret store — never hardcode credentials or URLs in test files or config
- `process.env.CI` — set automatically by GitHub Actions, GitLab CI, Azure DevOps, CircleCI, and most others
